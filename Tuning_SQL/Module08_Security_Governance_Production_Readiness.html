SSecurity giải quyết vấn đề gì?▼

Database là nơi lỗi bảo mật gây thiệt hại lớn nhất

Nếu app bị compromise nhưng database user chỉ có quyền tối thiểu, blast radius nhỏ hơn rất nhiều. Nếu migration không được review, một câu DDL sai có thể lock production. Nếu audit thiếu, bạn không biết ai đã đọc/xóa/sửa dữ liệu nhạy cảm.

Mental model: Performance làm hệ thống nhanh. Security và governance làm hệ thống đáng tin để vận hành lâu dài.

Dấu hiệu hệ thống chưa production-ready

  • App dùng quyền owner/admin để chạy query hằng ngày.
  • Mọi người dùng chung một database account.
  • Không có audit cho DDL, privilege change hoặc truy cập dữ liệu nhạy cảm.
  • Migration chạy thẳng production không có rollback plan.
S1 · Identity
Users, Roles & Grants
Role design tốt giúp tách quyền rõ ràng: app chạy app, migration chạy migration, DBA quản trị, analyst chỉ đọc.
RRole model chuẩn▼
Role/UserQuyềnKhông nên có
app_runtimeSELECT/INSERT/UPDATE/DELETE đúng schema/table cần thiếtDDL, GRANT, superuser
migration_userDDL theo pipelineDùng bởi app runtime
readonly_analystSELECT trên view/table được phépWrite, DDL, raw PII nếu không cần
dba_adminQuản trị có kiểm soátDùng chung tài khoản cá nhân
● ● ●roles-grants.sql
PostgreSQL
CREATE ROLE app_runtime LOGIN PASSWORD 'rotate-me';
GRANT USAGE ON SCHEMA app TO app_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO app_runtime;
ALTER DEFAULT PRIVILEGES IN SCHEMA app
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_runtime;

MySQL
CREATE USER 'app_runtime'@'10.%' IDENTIFIED BY 'rotate-me';
GRANT SELECT, INSERT, UPDATE, DELETE ON appdb.* TO 'app_runtime'@'10.%';

Oracle
CREATE USER app_runtime IDENTIFIED BY "rotate-me";
CREATE ROLE app_runtime_role;
GRANT CREATE SESSION TO app_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON app.orders TO app_runtime_role;
GRANT app_runtime_role TO app_runtime;
⚠️ Rule: Không để application dùng superuser/root/SYS/SYSTEM/schema owner để chạy workload bình thường.
S2 · Least Privilege
Least Privilege & Access Review
Quyền tối thiểu không phải để gây khó chịu. Nó giới hạn thiệt hại khi app bug, credential lộ hoặc người dùng thao tác sai.
PPermission review SQL▼
● ● ●permission-review.sql
PostgreSQL
SELECT grantee, table_schema, table_name, privilege_type
FROM information_schema.role_table_grants
WHERE table_schema = 'app'
ORDER BY grantee, table_name, privilege_type;

MySQL
SHOW GRANTS FOR 'app_runtime'@'10.%';

Oracle
SELECT grantee, owner, table_name, privilege
FROM dba_tab_privs
WHERE owner = 'APP'
ORDER BY grantee, table_name, privilege;

SELECT grantee, granted_role
FROM dba_role_privs
ORDER BY grantee;
Review itemCâu hỏi
App userCó DDL/GRANT/admin privilege không?
Readonly userCó đọc raw PII ngoài nhu cầu không?
Migration userCó dùng ngoài CI/CD pipeline không?
Human accessCó account cá nhân, MFA, audit trail không?
PPractice: tách quyền runtime/migration▼
Task — App đang dùng schema owner

Thiết kế lại quyền để app chỉ có DML, migration pipeline có DDL, analyst chỉ SELECT qua view đã mask PII.

Tạo 3 role riêng: runtime, migration, readonly. Runtime không có CREATE/ALTER/DROP/GRANT. Analyst đọc view như customer_public_view thay vì bảng raw.

S3 · Audit
Audit & Compliance
Audit giúp trả lời: ai truy cập dữ liệu nào, lúc nào, từ đâu, và đã thay đổi gì.
AAudit targets▼
Sự kiệnVì sao cần audit
Login failed/successPhát hiện brute force hoặc credential bị lộ
DDLAi thay đổi schema/index/constraint
Privilege changeAi cấp quyền nhạy cảm
Access PIICompliance, điều tra dữ liệu nhạy cảm
DELETE/TRUNCATE lớnĐiều tra data loss
● ● ●audit-examples.sql
PostgreSQL
-- PostgreSQL thường dùng pgaudit extension
shared_preload_libraries = 'pgaudit'
pgaudit.log = 'write, ddl, role'

MySQL
-- MySQL Enterprise Audit hoặc plugin audit tương đương
SHOW VARIABLES LIKE 'audit%';

Oracle
AUDIT CREATE TABLE;
AUDIT DROP ANY TABLE;
AUDIT GRANT ANY PRIVILEGE;

SELECT event_timestamp, dbusername, action_name, object_schema, object_name
FROM unified_audit_trail
ORDER BY event_timestamp DESC
FETCH FIRST 50 ROWS ONLY;
📌 Audit trade-off: Audit quá ít thì vô dụng, audit quá nhiều thì nhiễu và tốn storage. Bắt đầu với DDL, privilege, auth, write lớn và PII access.
S4 · Encryption
Encryption, TLS & Secret Rotation
Dữ liệu cần được bảo vệ khi lưu, khi truyền và khi credential bị xoay vòng.

LayerMục tiêuVí dụ

PostgreSQL
SHOW ssl;
SELECT * FROM pg_stat_ssl WHERE pid = pg_backend_pid();

MySQL
SHOW VARIABLES LIKE 'require_secure_transport';
SHOW STATUS LIKE 'Ssl_cipher';

Oracle
-- Kiểm tra network encryption thường qua sqlnet.ora / view cấu hình môi trường
-- SQLNET.ENCRYPTION_SERVER = REQUIRED
-- SQLNET.CRYPTO_CHECKSUM_SERVER = REQUIRED
RSecret rotation pattern▼
  1. Tạo credential mới song song credential cũ.
  2. Grant đúng quyền cho credential mới.
  3. Deploy app dùng secret mới.
  4. Quan sát connection mới đã dùng credential mới.
  5. Revoke/drop credential cũ.
  6. Ghi lại audit trail và rollback plan.
⚠️ Không rotate kiểu “đổi password trực tiếp” nếu app không hỗ trợ reload secret an toàn. Hãy dùng dual credentials để tránh downtime.
S5 · App Safety
SQL Injection Defense & Application Safety
DBA không viết toàn bộ app code, nhưng DBA phải biết dấu hiệu query nguy hiểm và thiết kế quyền để giảm thiệt hại.
QQuery safety rules▼
RuleVì sao
Parameterized queryKhông nối string user input vào SQL
Allowlist dynamic ORDER BY/table nameBind parameter không thay thế identifier
Least privilege app userInjection không thể DROP/ALTER nếu user không có quyền
Statement timeoutGiảm tác hại query runaway
Row-level security/view masking khi cầnGiảm lộ dữ liệu nhạy cảm
● ● ●safe-query-pattern.txt
-- Anti-pattern
sql = "SELECT * FROM users WHERE email = '" + input_email + "'"

-- Safe pattern
sql = "SELECT * FROM users WHERE email = ?"
params = [input_email]

-- Dynamic ORDER BY: dùng allowlist
allowed_sort = {"created_at", "email", "id"}
✅ DBA perspective: Nếu app user chỉ có DML trên vài table, SQL injection vẫn nguy hiểm nhưng blast radius nhỏ hơn nhiều so với app dùng owner/admin.
TTimeouts & guardrails▼
● ● ●timeouts.sql
PostgreSQL
ALTER ROLE app_runtime SET statement_timeout = '30s';
ALTER ROLE app_runtime SET idle_in_transaction_session_timeout = '60s';

MySQL

Oracle
-- Dùng Database Resource Manager/Profile để giới hạn resource/session

  SESSIONS_PER_USER 50
  IDLE_TIME 30;

SSenior answer templates▼

Q1: Bạn thiết kế quyền database cho app thế nào?

Tôi tách runtime user, migration user, readonly/analyst user và DBA admin. Runtime chỉ có DML cần thiết, không có DDL/GRANT/admin. Migration chạy qua pipeline có review. Human access dùng account cá nhân, audit, MFA hoặc jump host tùy môi trường.

Q2: Bạn audit gì trong database?

Tôi audit authentication, privilege changes, DDL, DELETE/TRUNCATE lớn và access vào dữ liệu nhạy cảm. Audit phải có retention, owner review và query/report để điều tra. Tôi tránh audit quá rộng gây nhiễu và tốn storage vô ích.

Q3: Làm sao deploy schema change an toàn?

Tôi dùng expand/contract migration: thêm cấu trúc mới backward-compatible, deploy app đọc/ghi cả hai nếu cần, backfill batch nhỏ, validate, chuyển traffic, rồi mới drop cấu trúc cũ. Trước khi chạy có đánh giá lock, plan rollback/forward-fix và monitoring.
