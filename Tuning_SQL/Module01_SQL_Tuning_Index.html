🎯 Index giải quyết vấn đề gì? ▼

Vấn đề gốc rễ: Full Table Scan

Không có index, mọi query đều phải đọc toàn bộ bảng từ đầu đến cuối. Với vài trăm row thì ổn, nhưng với vài triệu row — mỗi query có thể mất hàng giây hoặc hàng chục giây.

⚠️ Hiểu lầm phổ biến nhất: "Có index là query nhanh." — Sai! Có index nhưng index không được dùng, hoặc index không đủ tốt, query vẫn chậm như thường.

Index là gì (theo cách đơn giản nhất)?

Index là một sorted list + bảng tóm tắt phân cấp (B+Tree). Giống như mục lục từ điển — bạn không cần đọc từ trang 1, chỉ cần nhảy thẳng đến đúng vị trí.

💡 Mental model: Index = mục lục từ điển. Càng nhiều bảng có 10 triệu row, B+Tree chỉ cần 3–4 bước nhảy để tìm ra kết quả.

Tại sao cần học kỹ?

  • Index sai thứ tự cột → không được dùng (Nguyên tắc phễu)
  • Range condition đặt sai vị trí → scan dư hàng triệu row
  • Function trên cột → index vô dụng hoàn toàn
  • Database đôi khi bỏ qua index của bạn — và đôi khi nó đúng!

Lý thuyết nền — B+Tree & Cơ chế lưu trữ
WHY trước HOW: hiểu cơ chế lưu trữ để ra quyết định index đúng từ đầu.
📘 B+Tree Index — Beginner Level ▼

Hai điều cốt lõi cần nhớ

1) Index = sorted list + bảng tóm tắt phân cấp. Leaf nodes (tầng dưới) chứa giá trị đã sorted. Internal nodes (tầng trên) là "gáy sách" giúp nhảy nhanh.

2) Database tự quản lý index hoàn toàn. INSERT/UPDATE/DELETE đều tự cập nhật index. Càng nhiều index → write càng chậm hơn một chút.

💡 Mental model: Tìm "performance" trong từ điển 2000 trang: nhìn gáy sách → lật đến P → scan đến PE → tìm. 3 bước thay vì 2000 trang. Đó là B+Tree.

Trade-off cần hiểu ngay từ đầu

● ● ●index-tradeoff.txt
-- Bảng users có 5 index:
INSERT 1 row  → cập nhật 5 index  (chậm hơn 5x so với 0 index)
UPDATE email  → cập nhật 2 index  (chỉ index có cột email)
UPDATE bio    → cập nhật 0 index  (bio không trong index nào)
DELETE 1 row  → xóa khỏi 5 index

-- Thực tế: read:write = 90:10, nên 3–7 index/bảng là hợp lý
-- Hơn 10 index mà write chậm → review lại
📗 Heap Table vs Clustered Index — Intermediate Level ▼

Hai cách lưu trữ hoàn toàn khác nhau

🐘 PostgreSQL (Heap)
🐬 MySQL/InnoDB (Clustered)
🔶 Oracle (IOT)
PostgreSQL

Heap Table: Dữ liệu append vào cuối file, không quan tâm thứ tự PK. Mọi index (kể cả PK) đều trỏ đến physical location (ctid) của row.

● ● ●postgresql-heap.txt
── INDEX (email) ──         ── TABLE (heap) ──
alice@... → ctid (5,2) ───→ Page 5: [alice, 28, ...]
bob@...   → ctid (2,1) ───→ Page 2: [bob, 35, ...]

-- PK index hoạt động y hệt: chỉ thêm UNIQUE constraint
-- PK lookup = Secondary index lookup = 2 bước (index → heap)
-- Insert PK random (UUIDv4): ít bị ảnh hưởng hơn MySQL vì heap append
-- Nhưng PK/secondary index vẫn bị random insert; bảng lớn/write nhiều nên cân nhắc UUIDv7/ULID
✅ Lợi thế: Insert UUIDv4 thường nhẹ hơn MySQL vì data heap append, nhưng index vẫn phải cập nhật theo thứ tự random. Với workload ghi nhiều, ưu tiên key tăng dần hoặc gần tăng dần như UUIDv7/ULID.
MySQL / InnoDB

Clustered Index: PK chính là bảng. Dữ liệu lưu ngay trong leaf node của PK index, sắp xếp theo thứ tự PK. Không có heap riêng.

● ● ●mysql-clustered.txt
── PRIMARY KEY INDEX = TABLE ──
PK=1 → [alice, alice@..., 28, ...]  ← data nằm ngay đây!
PK=2 → [bob,   bob@...,   35, ...]
PK=3 → [charlie, ...]

── SECONDARY INDEX (email) ──
alice@... → PK=1  ← trỏ đến PK, không phải vị trí vật lý
bob@...   → PK=2

-- Secondary index lookup = 2 bước: sec.index → PK index
-- PK lookup = 1 bước: PK index có data ngay!
-- UUIDv4 làm PK: chậm hơn 3–10x vì insert vào vị trí random trong sorted tree
🚨 Hệ quả với MySQL: PK value được COPY vào mọi secondary index. PK = CHAR(36) UUID → mỗi secondary index entry nặng hơn 28 bytes so với BIGINT. Với 1M row, 5 secondary index → chênh 90MB chỉ vì chọn sai PK type!
Oracle

Heap Table (mặc định): Oracle mặc định dùng Heap Table tương tự PostgreSQL. Dữ liệu lưu theo ROWID (địa chỉ vật lý: file#.block#.row#).

Index-Organized Table (IOT): Tương đương Clustered Index của MySQL — toàn bộ dữ liệu lưu trong B+Tree theo thứ tự PK. Phải khai báo tường minh.

● ● ●oracle-storage.sql
-- Oracle mặc định: Heap Table
CREATE TABLE employees (
  emp_id   NUMBER PRIMARY KEY,
  name     VARCHAR2(100),
  dept_id  NUMBER
);
-- Index trỏ đến ROWID (vật lý: file#.block#.row#)
-- PK lookup = 2 bước: PK index → heap block

-- Index-Organized Table (IOT): dùng khi LUÔN query theo PK
CREATE TABLE lookup_codes (
  code_id  NUMBER        NOT NULL,
  code     VARCHAR2(20)  NOT NULL,
  meaning  VARCHAR2(200),
  CONSTRAINT pk_lookup PRIMARY KEY (code_id)
) ORGANIZATION INDEX;  -- ← từ khóa tạo IOT

-- Secondary index trên IOT → chứa "Logical ROWID" (PK + physical guess)
📌 Oracle ROWID: Dạng AAABcdAAEAAAAA7AAA — mã hóa (file, block, row) giúp truy cập trực tiếp đến vị trí vật lý mà không qua index. Đây là lý do Oracle heap lookup đôi khi nhanh hơn MySQL secondary index lookup.

So sánh 3 hệ quản trị

PostgreSQL
  • Heap mặc định
  • PK = UNIQUE index, không đặc biệt hơn
  • UUIDv4 PK: ít đau hơn MySQL, nhưng vẫn tốn chi phí ở index
  • CLUSTER command: sắp xếp lại heap 1 lần
  • PK lookup: 2 bước
MySQL/InnoDB
  • Clustered Index bắt buộc
  • PK = table, data nằm trong PK tree
  • UUIDv4 PK: rất chậm, dùng ULID/UUIDv7
  • PK value copy vào mọi secondary index
  • PK lookup: 1 bước
Oracle
  • Heap mặc định (như PostgreSQL)
  • IOT: tường minh với ORGANIZATION INDEX
  • ROWID: địa chỉ vật lý cực nhanh
  • Bitmap Index: cho cột cardinality thấp
  • Reverse Key Index: chống index hot-block

ORACLE
-- Oracle: dùng SEQUENCE thay vì AUTO_INCREMENT
CREATE SEQUENCE emp_seq
  START WITH 1
  INCREMENT BY 1

  NOCYCLE;

Anti-patterns cần tránh

🚨 MySQL: Dùng UUIDv4 (CHAR 36) làm PK → insert chậm 3–10x, secondary index phình 3x, RAM usage tăng cao. Dùng BINARY(16) + UUIDv7 hoặc BIGINT AUTO_INCREMENT thay thế.
🚨 Oracle: Không đặt CACHE cho SEQUENCE trong high-concurrency → mỗi nextval tốn 1 I/O → bottleneck. Luôn đặt CACHE 100+ cho production sequence.

S2 · Core Principles
4 Nguyên tắc vàng khi dùng Index
Nắm 4 nguyên tắc này = nắm 80% kiến thức về index. Khi gặp query chậm, áp dụng theo thứ tự.
① Nguyên tắc 1: Fast Lookup — Nhảy thẳng đến vị trí ▼

Thao tác cơ bản nhất: tìm một giá trị cụ thể gần như tức thì. Database nhảy qua internal nodes thay vì scan tuần tự.

💡 Sức mạnh O(log n): Từ 1.000 lên 1.000.000.000 row chỉ thêm 2 bước nhảy. Đừng lo lắng về kích thước index.
● ● ●fast-lookup.sql
SELECT * FROM movies WHERE release_year = 2019;

-- Index (release_year): [2015|2016|2017|2018|2019|2020|2021]
--                                             ↑ nhảy thẳng đến đây
-- Không cần đọc qua 2015, 2016, 2017, 2018...
② Nguyên tắc 2: Scan một chiều — Range + LIMIT siêu nhanh ▼

Sau khi nhảy đến vị trí, database đọc liên tục theo một hướng (leaf nodes liên kết nhau như linked list).

● ● ●range-scan.sql
SELECT * FROM users WHERE age >= 35 ORDER BY age ASC LIMIT 3;

-- Index (age): [18|22|25|28|30|35|37|42|48|55|61]
--                               ↑ Fast Lookup: age>=35
--                               35→37→42 ✓ DỪNG! (LIMIT 3)
-- Kết quả: chỉ đọc 3 entries thay vì scan 10M rows

-- Không có index: scan 10M → filter → sort → lấy 3
-- Có index:       nhảy đến 35 → đọc 3 → xong (vài ms vs vài giây)
📌 Lưu ý: Scan chỉ đi một hướng. ORDER BY col ASC và DESC dùng cùng 1 index được (scan ngược lại). Nhưng ORDER BY score DESC, created_at ASC cần index đúng hướng: (score DESC, created_at ASC).
③ Nguyên tắc 3: Từ trái sang phải — Nguyên tắc Phễu ▼

Composite index hoạt động như cái phễu: lọc từ trái sang phải, không được bỏ qua cột đầu tiên.

● ● ●funnel-principle.sql
-- Index: (country, lastname, firstname)
-- Sắp xếp: sort by country → trong mỗi country sort by lastname → ...

WHERE country = 'VN' AND lastname = 'Nguyen' AND firstname = 'Huy'
-- ✅ Dùng 3/3 bước phễu → tìm chính xác 1 entry

WHERE country = 'VN' AND lastname = 'Nguyen'
-- ✅ Dùng 2/3 bước phễu → OK

WHERE country = 'VN'
-- ✅ Dùng 1/3 bước phễu → OK nhưng kém tối ưu

WHERE lastname = 'Nguyen'
-- ❌ Bỏ qua country (cột đầu tiên) → KHÔNG dùng được index
--    Vì: 'Nguyen' nằm rải rác ở JP, US, VN... không liên tục
✅ Quy tắc thứ tự cột: Không phải "cột selective nhất lên đầu" — mà là cột nào được dùng ở query thường xuyên nhất thì lên đầu, để tối đa hóa số query được phục vụ bởi 1 index.
④ Nguyên tắc 4: Range phá vỡ phễu — Equality trước, Range sau ▼

Sau cột có range condition (>, <, BETWEEN), các cột tiếp theo trong index chỉ dùng để filter — không thu hẹp scan range được nữa.

● ● ●range-breaks-funnel.sql
WHERE country = 'VN' AND age > 28 AND married = 'yes'

-- ❌ Index (country, age, married):
--    country='VN' → phễu ✓
--    age>28       → range scan bắt đầu ✓
--    married='yes'→ sau range → chỉ filter, đọc CẢ rows có age>28
--    Đọc 6 entries, giữ 3 → lãng phí 50%

-- ✅ Index (country, married, age):
--    country='VN'  → phễu ✓
--    married='yes' → phễu ✓ (equality trước range!)
--    age>28        → range scan CHỈ trên block married='yes'
--    Đọc đúng 3 entries → không lãng phí!

-- QUY TẮC VÀNG: Equality columns TRƯỚC, Range column SAU

So sánh hỗ trợ Range trên 3 hệ quản trị

FeaturePostgreSQLMySQLOracle
Skip Scan / Loose Index Scan❌ Chưa hỗ trợ✅ Loose Index Scan (GROUP BY min/max)✅ Index Skip Scan
Bitmap AND/OR nhiều index✅ Bitmap Index Scan❌ Index Merge (hạn chế)✅ Bitmap Index (mạnh nhất)
Range scan descending✅✅ (MySQL 8+)✅
Partial Index✅ WHERE clause❌ Không hỗ trợ❌ Không hỗ trợ
📌 Oracle Index Skip Scan: Oracle có thể "nhảy qua" các cột đầu của composite index nếu cardinality thấp. Ví dụ index (gender, salary), query WHERE salary > 5000 có thể dùng được nhờ Skip Scan. Đây là lợi thế lớn so với PostgreSQL.

Index với từng SQL Operation
Áp dụng 4 nguyên tắc vào thực chiến — có ví dụ cho PostgreSQL, MySQL và Oracle.
🔍 WHERE: != · NULL · LIKE · Type mismatch ▼

Phép so sánh != (kẻ giết hiệu suất)

!= buộc database phải scan toàn bộ index vì kết quả nằm ở cả hai phía. Thường bị fall back về full table scan.

● ● ●not-equal.sql
-- ❌ Vấn đề: != không dùng index hiệu quả
WHERE status != 'open'

-- ✅ Fix 1: Thêm equality column để thu hẹp phạm vi
WHERE shop_id = 42 AND status != 'open'
-- Index (shop_id, status) → lookup shop_id trước → scan nhỏ hơn nhiều

-- ✅ Fix 2: Chuyển thành IN(...) nếu biết trước giá trị
WHERE status IN ('paid', 'cancelled', 'refunded')
-- Database tách thành 3 equality lookups → hiệu quả hơn

ORACLE
-- Oracle hỗ trợ <> và != như nhau
-- Oracle có thể dùng INDEX RANGE SCAN cho != nếu selectivity cao
-- Kiểm tra với EXPLAIN PLAN và nhìn ACCESS PREDICATES vs FILTER PREDICATES

NULL: Behavior khác nhau giữa các DB

● ● ●null-handling.sql
-- NULL sort order:
MySQL     NULL đứng TRƯỚC (nhỏ nhất)  → ASC: NULL, 1, 2, 3
PgSQL     NULL đứng SAU (lớn nhất)   → ASC: 1, 2, 3, NULL
Oracle    NULL đứng SAU (lớn nhất)   → ASC: 1, 2, 3, NULL

-- NULL-safe equality:
MySQL     WHERE col <=> NULL             -- NULL-safe operator
PgSQL     WHERE col IS NOT DISTINCT FROM NULL
Oracle    WHERE (col = val OR (col IS NULL AND val IS NULL))

-- Oracle đặc biệt: NULL KHÔNG được index trong B-tree index!
-- IS NULL query trên Oracle: full table scan nếu chỉ có B-tree index
Oracle Fix
CREATE INDEX idx_nullable ON t (col, 0);
-- Thêm cột hằng số → buộc Oracle index cả row có col=NULL
WHERE col IS NULL  -- Giờ dùng được index

LIKE và Type Mismatch

● ● ●like-type.sql
-- LIKE 'abc%' → range scan (OK với mọi DB)
-- LIKE '%abc%' → không dùng B-tree (cần Trigram/Full-text)

PostgreSQL
CREATE EXTENSION pg_trgm;
CREATE INDEX trgm_idx ON contacts USING GIN (name gin_trgm_ops);
WHERE name LIKE '%Nguyen%'  -- Dùng được với trigram index

Oracle
-- Oracle Text: Full-text search mạnh nhất
CREATE INDEX ft_idx ON contacts (name)
  INDEXTYPE IS ctxsys.context;
WHERE CONTAINS(name, 'Nguyen') > 0  -- Full-text search

-- Type Mismatch (MySQL đặc biệt nguy hiểm):
MySQL Bug
-- cột payment_id VARCHAR: so sánh với số → CAST cột → index vô dụng
WHERE payment_id = 57013925718   -- ❌ Tự CAST(payment_id AS UNSIGNED)
WHERE payment_id = '57013925718' -- ✅ string = string → index OK
📊 ORDER BY · GROUP BY · DISTINCT ▼

ORDER BY: Tránh filesort bằng mọi giá

● ● ●order-by.sql
-- Bảng issues, query thường xuyên:
SELECT * FROM issues
WHERE type = 'bug'
ORDER BY severity DESC, created_at DESC;

-- ✅ Index: (type, severity DESC, created_at DESC)
--    1. Fast Lookup: type='bug'
--    2. Scan descending → đã đúng thứ tự → KHÔNG cần filesort

PostgreSQL
CREATE INDEX ON issues (type, severity DESC, created_at DESC);
-- Tăng work_mem nếu vẫn bị sort: SET work_mem = '64MB';

MySQL 8+
CREATE INDEX ON issues (type, severity DESC, created_at DESC);
-- MySQL 5.x: chỉ ASC — MySQL 8+ mới hỗ trợ DESC trong index
-- Tăng sort_buffer_size: SET sort_buffer_size = 8*1024*1024;

Oracle
CREATE INDEX ON issues (type, severity DESC, created_at DESC);
-- Oracle hỗ trợ ASC/DESC từ version 8i
-- Kiểm tra EXPLAIN PLAN: không có SORT ORDER BY → index đang dùng đúng

GROUP BY: Cột WHERE trước, GROUP BY sau

● ● ●group-by.sql
SELECT is_paying, gender, COUNT(*) FROM users
WHERE onboarding = 'yes'
GROUP BY is_paying, gender;

-- Index: (onboarding, is_paying, gender)
-- ✅ Workflow: lookup onboarding → scan sorted (is_paying, gender)
--    → loop-and-count algorithm → không cần temp hash table

-- Thêm aggregate cột vào index → index-only operation:
SELECT is_paying, gender, AVG(projects_cnt) FROM users
GROUP BY is_paying, gender;
-- Index: (is_paying, gender, projects_cnt)
--        ↑ WHERE/GROUP BY       ↑ aggregate cột: đọc từ index, không cần load row!

Oracle đặc biệt
-- Oracle hỗ trợ Bitmap Index — cực mạnh cho GROUP BY nhiều cột boolean/status
CREATE BITMAP INDEX bmp_paying ON users (is_paying);
CREATE BITMAP INDEX bmp_gender ON users (gender);
-- Oracle tự BITMAP AND các index → không cần composite index
-- CHỈ dùng Bitmap Index trên OLAP/DWH, KHÔNG dùng trên OLTP (lock cả block!)
🔗 JOIN: Nested Loop, Hash Join & Lateral ▼

Nested Loop: Index cho bảng bị probe

● ● ●join-index.sql
SELECT e.* FROM employee e
JOIN department d ON e.department_id = d.department_id
WHERE e.salary > 100000 AND d.country = 'VN';

-- Hướng 1 (employee driving): lọc employee trước, probe department
CREATE INDEX ON employee (salary);
CREATE INDEX ON department (department_id, country);

-- Hướng 2 (department driving): lọc department trước, probe employee
CREATE INDEX ON department (country);
CREATE INDEX ON employee (department_id, salary);

-- Không mặc định tạo cả 4 index. Chọn theo plan thực tế, tần suất query và write cost.
-- Nested Loop nhanh khi inner/probe side có index phù hợp.

Oracle
-- Oracle hỗ trợ USE_NL, USE_HASH, USE_MERGE hints để ép join algorithm:
SELECT /*+ USE_NL(e d) */ e.* FROM employee e JOIN department d ...
-- USE_NL: ép Nested Loop (tốt khi driving table nhỏ + index đủ)
-- USE_HASH: ép Hash Join (tốt khi cả 2 bảng lớn, không có index join)

Lateral Join (PostgreSQL / Oracle 12c+)

● ● ●lateral-join.sql
PostgreSQL
SELECT c.*, recent.*
FROM customers c
LEFT JOIN LATERAL (
  SELECT * FROM sales s
  WHERE s.customer_id = c.id
  ORDER BY created_at DESC LIMIT 3
) recent ON TRUE;
-- Index cần: (customer_id, created_at DESC) trên bảng sales
-- Mỗi customer chỉ đọc 3 entries → cực nhanh

Oracle 12c+
SELECT c.*, recent.*
FROM customers c,
  LATERAL (
    SELECT * FROM sales s
    WHERE s.customer_id = c.id
    ORDER BY created_at DESC FETCH FIRST 3 ROWS ONLY
  ) recent;
-- Oracle dùng FETCH FIRST N ROWS ONLY thay vì LIMIT

Mục tiêu: Tạo bảng mẫu, tạo dữ liệu, chạy EXPLAIN, phân tích và tạo index phù hợp.

Bước thực hiện:

  1. Tạo bảng orders với 100,000+ rows (dùng generate_series hoặc script)
  2. Chạy query: WHERE status='pending' AND region='HN' ORDER BY total DESC LIMIT 10
  3. Chạy EXPLAIN ANALYZE → ghi lại execution time
  4. Xác định index cần tạo dựa trên 4 nguyên tắc
  5. Tạo index → chạy lại EXPLAIN ANALYZE → so sánh
● ● ●practice-task1.sql
PostgreSQL
CREATE TABLE orders (
  id         BIGSERIAL PRIMARY KEY,
  status     VARCHAR(20),
  region     VARCHAR(10),
  total      NUMERIC(12,2),
  created_at TIMESTAMP DEFAULT NOW()
);

INSERT INTO orders (status, region, total)
SELECT
  (ARRAY['pending','paid','cancelled'])[ceil(random()*3)],
  (ARRAY['HN','HCM','DN'])[ceil(random()*3)],
  round((random()*10000000)::numeric, 2)
FROM generate_series(1, 100000);

-- Chạy query chậm:
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE status = 'pending' AND region = 'HN'
ORDER BY total DESC LIMIT 10;

-- Câu hỏi: Index nào bạn sẽ tạo?
💡 Xem lời giải

Index đúng: (status, region, total DESC)

Lý do: status và region là equality conditions (Nguyên tắc phễu) → đặt trước. total là cột ORDER BY → đặt sau với hướng DESC để tránh filesort. Database sẽ Fast Lookup đến (pending, HN), rồi scan descending lấy 10 entries đầu mà không cần sort.

● ● ●solution-task1.sql
CREATE INDEX idx_orders_search
  ON orders (status, region, total DESC);

💡 Xem lời giải
● ● ●find-unused-index.sql
PostgreSQL
SELECT schemaname, tablename, indexrelname,
       idx_scan AS scans, idx_tup_read
FROM pg_stat_all_indexes
WHERE schemaname = 'public'
  AND idx_scan = 0
  AND indexrelname NOT LIKE '%pkey%'
ORDER BY pg_relation_size(indexrelid) DESC;

MySQL
SELECT object_name, index_name, count_star
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_schema = 'mydb'
  AND count_star = 0
  AND index_name IS NOT NULL
ORDER BY object_name, index_name;

Oracle

JOIN v$object_usage u ON i.index_name = u.index_name
WHERE u.used = 'NO';

🔬 Index-only Query & Kỹ thuật đặc biệt của Oracle ▼
● ● ●index-only-oracle-special.sql
── INDEX-ONLY QUERY ─────────────────────────────────────
-- Đưa đủ cột vào index → không cần load row từ table

PostgreSQL (INCLUDE)
CREATE INDEX ON invoices (customer_id, year) INCLUDE (price);
-- price không ảnh hưởng thứ tự sort, không ảnh hưởng UNIQUE constraint
-- Nhưng vẫn dùng được cho index-only query:
SELECT customer_id, year, SUM(price) FROM invoices
WHERE customer_id = 42 GROUP BY customer_id, year;
-- → Không chạm vào heap table!

MySQL
-- Không có INCLUDE → đưa cột vào cuối index:

Oracle
-- Oracle: Index Fast Full Scan = đọc toàn index như table
-- Tốt khi query cần nhiều row từ index (không cần table access)
CREATE INDEX idx_inv_cov ON invoices (customer_id, year, price);
-- Nếu EXPLAIN PLAN hiện INDEX FAST FULL SCAN → query chỉ đọc index

── ORACLE ĐẶC BIỆT: Reverse Key Index ──────────────────
Oracle Only
-- Vấn đề: sequence PK luôn tăng → insert vào cùng 1 block → hot block
-- Giải pháp: REVERSE KEY → bytes đảo ngược → phân phối đều
CREATE INDEX idx_seq_pk ON orders (order_id) REVERSE;
-- Nhược điểm: không dùng được Range Scan! Chỉ dùng Unique Scan
-- Chỉ dùng khi: high-concurrency insert, query luôn là = (không range)

── ORACLE ĐẶC BIỆT: Bitmap Index ───────────────────────
Oracle OLAP
CREATE BITMAP INDEX bmp_status ON orders (status);
CREATE BITMAP INDEX bmp_region ON orders (region);
-- Oracle tự BITMAP AND các kết quả:
WHERE status = 'paid' AND region = 'HN'
-- → Bitmap AND: nhanh gấp 10x cho DWH queries
-- ⚠️ KHÔNG dùng trên OLTP: row-level UPDATE lock cả bitmap block!
⚠️ Oracle Bitmap Index và OLTP: Bitmap Index rất mạnh cho DWH/OLAP nhưng gây lock block khi UPDATE/INSERT concurrent. Trên hệ thống OLTP (nhiều transaction đồng thời), tuyệt đối không dùng Bitmap Index.

🔧 Debug workflow — Khi query chậm ▼

Làm theo thứ tự này khi gặp query chậm

  1. Đo thời gian thực tế — không đoán mò. Chạy query nhiều lần, lấy thời gian trung bình.
  2. Chạy EXPLAIN/EXPLAIN ANALYZE/AUTOTRACE — xem plan được chọn, estimated vs actual rows.
  3. Kiểm tra statistics — nếu estimated ≠ actual nhiều → chạy ANALYZE/GATHER_TABLE_STATS.
  4. Tìm bottleneck — Full scan? Filesort? Nhiều row load nhưng ít row trả về? JOIN lớn?
  5. Áp dụng 4 nguyên tắc — tạo index phù hợp, tránh function trên cột, equality trước range.
  6. Test lại với EXPLAIN — xác nhận plan mới, đo thời gian mới.

🎯 Senior-level questions (open-ended) ▼
Senior Q1: Database có index mà vẫn không dùng — debug như thế nào?

Gợi ý các điểm cần đề cập:

  • Chạy EXPLAIN/EXPLAIN PLAN/AUTOTRACE để xem plan thực tế
  • Kiểm tra các nguyên nhân phổ biến: function trên cột, type mismatch, bỏ qua cột đầu composite index, != condition
  • Kiểm tra statistics có cũ không → ANALYZE/GATHER_TABLE_STATS

💡 Xem sample answer

Tôi sẽ bắt đầu bằng EXPLAIN ANALYZE (PostgreSQL) hoặc EXPLAIN PLAN + DBMS_XPLAN (Oracle) để xem plan thực tế. Nếu plan là full scan dù có index, tôi kiểm tra 4 nguyên nhân theo thứ tự ưu tiên: (1) function trên cột như YEAR(), LOWER() — fix bằng cách viết lại query hoặc tạo functional index; (2) type mismatch — fix bằng cách đảm bảo kiểu dữ liệu khớp; (3) vi phạm nguyên tắc phễu — fix bằng cách thêm cột đầu tiên vào WHERE; (4) statistics cũ — fix bằng ANALYZE. Nếu tất cả điều kiện đúng mà database vẫn full scan, tôi sẽ xem xét rằng database có thể đúng: khi query match > 10–30% rows, random I/O qua index có thể đắt hơn sequential full scan. Với Oracle tôi có thể dùng hint INDEX() để force test và so sánh thời gian thực tế.

Senior Q2: Thiết kế index cho bảng orders 50 triệu rows với các query phổ biến

Context: Bảng orders(id, customer_id, status, region, total, created_at). Các query phổ biến: (1) Tìm order của customer, sort mới nhất. (2) Dashboard: count theo status + region. (3) Xóa orders cũ hơn 2 năm hàng tháng.

  • Áp dụng 4 nguyên tắc cho từng query
  • Xem xét composite index bao phủ nhiều query nhất
  • Đề xuất partition cho xóa data lớn
  • So sánh cách tiếp cận trên PostgreSQL vs MySQL vs Oracle
💡 Xem sample answer
● ● ●senior-q2-solution.sql
-- Q1: Customer orders, sorted by created_at DESC
CREATE INDEX idx_orders_customer
  ON orders (customer_id, created_at DESC);
-- Phễu: customer_id equality → scan created_at descending → LIMIT dừng sớm

-- Q2: Dashboard count theo status + region
CREATE INDEX idx_orders_dashboard
  ON orders (status, region, created_at);
-- Hoặc index-only: thêm total nếu cần SUM(total)

-- Q3: Xóa data cũ → dùng PARTITION thay vì DELETE
PostgreSQL
CREATE TABLE orders PARTITION BY RANGE (created_at);
-- Tạo partition theo tháng → DROP PARTITION cũ = vài giây

Oracle
-- Oracle hỗ trợ Interval Partition: tự tạo partition mới
CREATE TABLE orders (...) PARTITION BY RANGE (created_at)
INTERVAL (NUMTOYMINTERVAL(1, 'MONTH'))
(PARTITION p_init VALUES LESS THAN (DATE '2024-01-01'));
-- Mỗi tháng Oracle tự tạo partition mới → TRUNCATE PARTITION để xóa
Senior Q3: Khác biệt quan trọng nhất giữa PostgreSQL, MySQL và Oracle khi thiết kế index?
  • MySQL: Clustered Index, PK size ảnh hưởng toàn bộ secondary index, tránh UUIDv4
  • PostgreSQL: Heap Table, Partial Index, Trigram Index, INCLUDE clause
  • Oracle: Bitmap Index cho OLAP, Skip Scan, Function-based Index, IOT, NULL không được index
💡 Xem sample answer

Ba điểm khác biệt quan trọng nhất: (1) Lưu trữ data: MySQL/InnoDB dùng Clustered Index — PK là bảng, data nằm trong PK tree, PK size ảnh hưởng mọi secondary index nên phải chọn PK nhỏ và time-ordered. PostgreSQL và Oracle mặc định dùng Heap Table — tất cả index bình đẳng. (2) Tính năng đặc biệt: PostgreSQL có Partial Index (WHERE clause trong CREATE INDEX) và Trigram Index cho full-text; Oracle có Bitmap Index cực mạnh cho OLAP/DWH nhưng nguy hiểm trong OLTP, và Index Skip Scan cho phép bỏ qua cột đầu composite index; MySQL thiếu cả hai. (3) NULL handling: Oracle không index NULL trong B-tree — phải workaround để IS NULL query dùng được index. PostgreSQL và MySQL không có vấn đề này.
