OOperations giải quyết vấn đề gì?▼

Tuning là phản ứng, monitoring là chủ động

Query tuning xử lý từng vấn đề cụ thể. Operations giúp bạn thấy xu hướng trước khi sự cố xảy ra: latency tăng, slow query mới xuất hiện, replication lag, backup lỗi, table bloat, disk gần đầy.

Mental model: Database production là hệ thống sống. Nếu không đo nhịp tim, bạn chỉ biết nó bệnh khi nó ngã.

Dấu hiệu bạn thiếu operations

  • Không biết query nào tốn tài nguyên nhất tuần này.
  • Backup chạy nhưng chưa từng restore thử.
  • Disk đầy bất ngờ vì index/table growth.
  • Replica lag làm dữ liệu đọc bị cũ nhưng app không biết.

S2 · SQL Observability
Slow Query & SQL Statistics
Query chậm nhất không phải lúc nào cũng nguy hiểm nhất. Query chạy 10ms nhưng 1 triệu lần/ngày cũng có thể là thủ phạm.
STop SQL trên 3 hệ quản trị▼
● ● ●top-sql.sql
PostgreSQL
-- Cần extension pg_stat_statements
SELECT queryid, calls,
       total_exec_time,
       mean_exec_time,
       rows,
       query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

MySQL
SELECT digest_text, count_star,
       sum_timer_wait/1000000000000 AS total_sec,
       avg_timer_wait/1000000000000 AS avg_sec
FROM performance_schema.events_statements_summary_by_digest
ORDER BY sum_timer_wait DESC
LIMIT 20;

Oracle
SELECT sql_id, executions,
       elapsed_time/1000000 AS elapsed_sec,
       cpu_time/1000000 AS cpu_sec,
       buffer_gets,
       disk_reads,
       sql_text
FROM v$sql
WHERE executions > 0
ORDER BY elapsed_time DESC
FETCH FIRST 20 ROWS ONLY;
📌 Phân tích top SQL: nhìn cả total time, average time, calls, rows, buffer reads, disk reads và plan hash. Một query “trung bình” nhưng gọi cực nhiều có thể đáng tối ưu hơn query rất chậm nhưng hiếm.

● ● ●slow-query-settings.sql

MySQL

Oracle

S3 · Object Health
Table, Index Health & Statistics Freshness
Bảng và index cũng “già đi”: phình, stats cũ, index không dùng, fragmentation và vacuum/purge chậm.
IUnused index & object size▼
● ● ●object-health.sql
PostgreSQL
SELECT schemaname, relname, indexrelname,
       idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
JOIN pg_index ON pg_index.indexrelid = pg_stat_user_indexes.indexrelid
WHERE idx_scan = 0
  AND NOT indisunique
ORDER BY pg_relation_size(indexrelid) DESC;

MySQL
SELECT object_schema, object_name, index_name
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NOT NULL
  AND count_star = 0;

Oracle
SELECT owner, segment_name, segment_type,
       bytes/1024/1024 AS mb
FROM dba_segments
WHERE owner = 'APP'
ORDER BY bytes DESC
FETCH FIRST 30 ROWS ONLY;
⚠️ Không drop index chỉ vì idx_scan = 0: Kiểm tra thời gian reset stats, unique/constraint, query seasonal, report cuối tháng và plan regression trước.
VBloat, vacuum, stats freshness▼
● ● ●stats-vacuum.sql
PostgreSQL
SELECT relname, n_live_tup, n_dead_tup,
       last_vacuum, last_autovacuum,
       last_analyze, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;

MySQL
ANALYZE TABLE orders;
OPTIMIZE TABLE orders;

Oracle
SELECT owner, table_name, stale_stats, last_analyzed
FROM dba_tab_statistics
WHERE owner = 'APP'
ORDER BY last_analyzed NULLS FIRST;

EXEC DBMS_STATS.GATHER_SCHEMA_STATS(ownname => 'APP', cascade => TRUE);
S4 · Resource Health
Cache, Memory & I/O
Nếu query plan tốt nhưng vẫn chậm, tài nguyên có thể đang bão hòa: cache miss, temp spill, I/O wait hoặc connection saturation.
CCache hit & I/O pressure▼
● ● ●cache-io.sql
PostgreSQL
SELECT datname,
       blks_hit,
       blks_read,
       round(blks_hit * 100.0 / nullif(blks_hit + blks_read, 0), 2) AS cache_hit_pct
FROM pg_stat_database
ORDER BY cache_hit_pct;

MySQL
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
SHOW ENGINE INNODB STATUS;

Oracle
SELECT name, value
FROM v$sysstat
WHERE name IN (
  'db block gets',
  'consistent gets',
  'physical reads'
);

SELECT event, total_waits, time_waited
FROM v$system_event
WHERE wait_class <> 'Idle'
ORDER BY time_waited DESC;
TTemp spill & memory pressure▼

Sort/hash aggregate/hash join có thể spill ra disk nếu memory không đủ. Khi đó plan nhìn hợp lý nhưng runtime vẫn chậm vì temp I/O.

MySQLCreated_tmp_disk_tables tăngIndex cho ORDER/GROUP, tune temp table size

Backup không có giá trị nếu bạn chưa từng restore thành công trong thời gian RTO cho phép.

● ● ●backup-commands.txt
PostgreSQL
pg_basebackup -h primary -D /backup/base -Fp -Xs -P

MySQL
mysqldump --single-transaction --routines --triggers appdb > appdb.sql

Oracle RMAN
RMAN> BACKUP DATABASE PLUS ARCHIVELOG;
RMAN> RESTORE DATABASE;
RMAN> RECOVER DATABASE;
🚨 Production rule: Lịch backup phải đi kèm lịch restore drill. Không có restore drill thì chưa thể nói backup an toàn.
PRestore drill checklist▼
  1. Lấy backup mới nhất từ storage thật.
  2. Restore vào môi trường cô lập.
  3. Chạy migration/schema check nếu cần.
  4. Chạy query kiểm tra số dòng, checksum/balance quan trọng.
  5. Đo thời gian restore thực tế so với RTO.
  6. Ghi lại runbook và lỗi gặp phải.
S6 · Replication & Capacity
Replication, Connection Pool & Capacity Planning
Khi hệ thống lớn lên, bottleneck thường chuyển từ query đơn lẻ sang replication lag, connection storm, disk growth và saturation.
RReplication lag▼
● ● ●replication-lag.sql
PostgreSQL
SELECT application_name, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS bytes_lag
FROM pg_stat_replication;

MySQL
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source, Replica_IO_Running, Replica_SQL_Running

Oracle Data Guard
SELECT name, value, unit
FROM v$dataguard_stats;

SELECT process, status, thread#, sequence#
FROM v$managed_standby;
⚠️ Read replica: App phải biết dữ liệu trên replica có thể cũ. Các flow read-after-write nên đọc primary hoặc dùng cơ chế chờ lag.

S7 · Interview Prep
Interview Prep — Database Operations
Phần này kiểm tra tư duy vận hành: bạn có biết bảo vệ database trước sự cố thật hay không.
QQuick quiz▼

SSenior answer templates▼

Q1: Bạn thiết kế monitoring database tối thiểu thế nào?

Tôi bắt đầu từ user-facing signals như latency/error, rồi thêm database internals: active connections, slow/top SQL, lock wait/deadlock, replication lag, disk free/growth, cache hit/temp spill, backup status. Mỗi alert có threshold theo thời gian và runbook xử lý.

Q2: Backup strategy tốt cần gì?

Cần định nghĩa RPO/RTO, full/incremental/PITR tùy DB, lưu backup ngoài failure domain, mã hóa, kiểm tra integrity và restore drill định kỳ. Chỉ khi restore thành công trong thời gian RTO thì backup mới được coi là đáng tin.

Q3: Replica lag ảnh hưởng app thế nào?

Replica lag làm read replica trả dữ liệu cũ. Các flow cần read-after-write consistency phải đọc primary, route theo session, hoặc chờ replica bắt kịp. Monitoring phải alert khi lag vượt ngưỡng nghiệp vụ, không chỉ khi replication chết.
