RMigration giải quyết vấn đề gì?▼

Schema change không chỉ là chạy SQL

Một câu ALTER TABLE đơn giản trên local có thể lock bảng hàng phút ở production. Một backfill lớn có thể làm WAL/binlog/redo tăng mạnh, replication lag, cache bị đẩy ra và rollback cực lâu.

Mental model: Migration production là phẫu thuật khi hệ thống đang sống. Mục tiêu không phải chỉ “xong”, mà là xong với rủi ro đo được.

Migration Strategy & Risk Review
Mỗi migration cần được review theo lock impact, compatibility, rollback, observability và dữ liệu bị chạm tới.
CChange review matrix▼

S2 · Zero Downtime
Expand / Contract Migration
Pattern cơ bản để thay schema mà app version cũ và mới có thể chạy song song.
FFlow đổi cột an toàn▼
● ● ●expand-contract.txt
EXPAND
  1. Add nullable new column / new table
  2. Deploy app write cả old + new
  3. Backfill old → new theo batch
  4. Validate old/new match

CUTOVER
  5. Deploy app read new
  6. Monitor errors, lag, mismatch

CONTRACT
  7. Stop writing old
  8. Drop old column/table sau retention window
● ● ●expand-contract.sql
-- Bước 1: expand, không NOT NULL ngay
ALTER TABLE users ADD COLUMN email_normalized VARCHAR(255);

-- Bước 3: backfill batch
UPDATE users
SET email_normalized = LOWER(email)
WHERE email_normalized IS NULL
  AND id BETWEEN :from_id AND :to_id;

-- Bước cuối sau khi validate: add constraint/drop old nếu cần
S3 · Online DDL
Online DDL & Online Index Creation
Index và DDL trên bảng lớn cần cú pháp online/concurrent và cần giám sát I/O/replication lag.
IOnline index trên 3 DB▼
● ● ●online-index.sql
PostgreSQL
CREATE INDEX CONCURRENTLY idx_orders_user_created
ON orders(user_id, created_at DESC);

-- Không chạy trong transaction block

MySQL
ALTER TABLE orders
  ADD INDEX idx_orders_user_created(user_id, created_at),
  ALGORITHM=INPLACE,
  LOCK=NONE;

Oracle
CREATE INDEX idx_orders_user_created
ON orders(user_id, created_at)
ONLINE;
⚠️ Online không nghĩa là miễn phí: Online index vẫn dùng CPU/I/O/temp/redo/WAL/binlog và có thể làm replica lag.
CConstraint validation an toàn▼
● ● ●constraint-validation.sql
PostgreSQL
ALTER TABLE orders
ADD CONSTRAINT chk_total_non_negative
CHECK (total_amount >= 0) NOT VALID;

ALTER TABLE orders VALIDATE CONSTRAINT chk_total_non_negative;

Oracle
ALTER TABLE orders
ADD CONSTRAINT chk_total_non_negative
CHECK (total_amount >= 0)
ENABLE NOVALIDATE;
S4 · Backfill
Backfill, Throttling & Data Validation
Backfill tốt phải chạy được nhiều lần, dừng được, resume được và không làm production nghẽn.
BBatch backfill pattern▼
● ● ●batch-backfill.sql
PostgreSQL
WITH batch AS (
  SELECT id
  FROM users
  WHERE email_normalized IS NULL
  ORDER BY id
  LIMIT 5000
)
UPDATE users u
SET email_normalized = LOWER(email)
FROM batch b
WHERE u.id = b.id;

Oracle
UPDATE users
SET email_normalized = LOWER(email)
WHERE email_normalized IS NULL
  AND ROWNUM <= 5000;
✅ Backfill rule: Commit từng batch nhỏ, sleep/throttle khi lag hoặc load tăng, và lưu progress để resume.
VValidation & reconciliation▼
● ● ●validate-migration.sql
-- Đếm rows chưa backfill
SELECT COUNT(*)
FROM users
WHERE email_normalized IS NULL;

-- Kiểm tra mismatch
SELECT id, email, email_normalized
FROM users
WHERE email_normalized <> LOWER(email)
FETCH FIRST 100 ROWS ONLY;
S5 · Cutover
Cutover, Feature Flags & Rollback
Cutover là thời điểm chuyển production sang đường mới. Cần feature flag, validation và rollback/forward-fix rõ ràng.
CCutover checklist▼
  1. Backfill hoàn tất và validation pass.
  2. App đã dual-write hoặc old/new compatible.
  3. Feature flag cho read path mới sẵn sàng.
  4. Dashboard theo dõi error, latency, lock, replication lag.
  5. Rollback hoặc forward-fix được viết sẵn.
  6. Owner, thời điểm, kênh war-room rõ ràng.
● ● ●cutover-flow.txt
Before cutover  validate old = new
      │
      ▼
Enable read_new flag for 1%
      │ monitor
      ▼
Ramp 10% → 50% → 100%
      │
      ├─ bad: disable flag, investigate
      └─ good: freeze old path, schedule cleanup

S6 · Version Upgrades
Database Version Upgrades
Upgrade version không chỉ là chạy installer. Nó là compatibility test, performance baseline, extension/plugin check và rollback plan.
UUpgrade plan▼
BướcMục tiêu
InventoryVersion, extensions/plugins, parameters, deprecated features
Staging restoreRestore production-like backup lên version mới
Compatibility testApp test, migration test, SQL regression test
Performance baselineTop SQL trước/sau, plan regression
Cutover planBlue/green, replica upgrade, logical replication hoặc downtime window
RollbackDowngrade có hỗ trợ không? Backup trước upgrade ở đâu?
● ● ●upgrade-checks.sql
PostgreSQL
SELECT version();
SELECT extname, extversion FROM pg_extension;

MySQL
SELECT VERSION();
SHOW PLUGINS;

Oracle
SELECT * FROM v$version;
SELECT comp_name, version, status FROM dba_registry;
⚠️ Major upgrade: Không assume plan giữ nguyên. Luôn so top SQL, execution plan và latency trước/sau.
S7 · Interview Prep
Interview Prep — Migration & Upgrades
Câu hỏi tập trung vào tư duy giảm rủi ro production change.
QQuick quiz▼
Vì sao expand/contract migration an toàn hơn drop/rename trực tiếp?

B. Vì hỗ trợ backward compatibility và rollback tốt hơn
C. Vì không cần validate dữ liệu
Online index có nghĩa là gì?
A. Không tốn tài nguyên
B. Giảm blocking nhưng vẫn cần theo dõi tài nguyên
C. Chỉ tạo metadata giả
SSenior answer templates▼

Q1: Bạn thêm cột NOT NULL cho bảng 500M rows thế nào?

Tôi không add NOT NULL + default trực tiếp nếu có nguy cơ rewrite/lock lớn. Tôi thêm cột nullable, deploy app dual-write, backfill batch nhỏ, validate không còn null, sau đó add constraint/NOT NULL theo cách an toàn của DB và cuối cùng cleanup code cũ.

Q2: Backfill production cần guardrail gì?

Batch nhỏ, commit từng batch, progress tracking, idempotent, throttle theo CPU/I/O/replica lag, timeout rõ, có pause/resume, validation query và rollback/forward-fix plan.

Q3: Major version upgrade cần test gì?

Tôi restore bản production-like lên version mới, chạy app regression, migration suite, top SQL benchmark, so execution plan, kiểm tra extension/plugin/deprecated features, backup/restore, replication/failover và rollback path.
