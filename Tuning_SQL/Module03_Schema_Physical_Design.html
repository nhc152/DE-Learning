Index không cứu được schema sai

Index và query tuning chỉ tối ưu trên cấu trúc dữ liệu đã có. Nếu kiểu dữ liệu sai, PK quá lớn, dữ liệu bán cấu trúc bị nhét vào JSON vô tội vạ hoặc thiếu constraint, database sẽ phải trả giá ở mọi query và mọi thao tác ghi.

Mental model: Schema là đường ray. Query và index là con tàu. Đường ray cong sai từ đầu thì tàu có mạnh cũng không chạy ổn định.

Sau module này bạn phải làm được

  • Chọn primary key và data type phù hợp với PostgreSQL, MySQL/InnoDB, Oracle.
  • Thiết kế constraint để dữ liệu không bẩn và query plan dễ dự đoán.
  • Quyết định khi nào dùng JSON, partition, materialized view hoặc summary table.
  • Giải thích trade-off giữa normalized schema, denormalization và pre-computation.
S1 · Foundation
Primary Key & Data Type Design
Primary key và kiểu dữ liệu là quyết định rất khó sửa sau khi hệ thống đã có dữ liệu lớn.

● ● ●primary-key-design.sql
-- MySQL/InnoDB: PK nhỏ và tăng dần giúp clustered index ổn định
CREATE TABLE orders (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  created_at DATETIME NOT NULL
);

-- PostgreSQL: UUIDv7/ULID vẫn nên lưu dạng compact nếu dùng làm PK
CREATE TABLE events (
  id uuid PRIMARY KEY,
  aggregate_id uuid NOT NULL,
  created_at timestamptz NOT NULL
);
⚠️ Rule: Với MySQL/InnoDB, PK nằm trong mọi secondary index. PK càng to, toàn bộ database càng phình.
DData type ảnh hưởng index▼

Chọn kiểu nhỏ nhất nhưng đủ nghĩa

  • Dùng BIGINT cho ID nếu có khả năng vượt INT.
  • Không lưu số tiền bằng FLOAT; dùng DECIMAL/NUMERIC hoặc integer minor unit.
  • Không lưu ngày giờ dạng string; dùng kiểu date/timestamp native.
  • Tránh so sánh khác kiểu vì có thể khiến database cast cột và bỏ index.
● ● ●type-mismatch.sql
-- Anti-pattern: phone là VARCHAR nhưng query truyền số
WHERE phone = 84901234567

-- Đúng: so sánh cùng kiểu
WHERE phone = '84901234567'
S2 · Data Integrity
Constraint, UNIQUE & NULL
Constraint không chỉ để bắt lỗi. Nó là hợp đồng dữ liệu giúp app đơn giản hơn và giúp optimizer có thêm thông tin.
CConstraint là hàng rào cuối cùng▼
● ● ●constraints.sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  status VARCHAR(20) NOT NULL,
  total_amount NUMERIC(12,2) NOT NULL,
  created_at TIMESTAMP NOT NULL,
  CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES users(id),
  CONSTRAINT chk_orders_status CHECK (status IN ('pending','paid','cancelled')),
  CONSTRAINT chk_orders_total CHECK (total_amount >= 0)
);
✅ DBA mindset: Nếu dữ liệu sai không thể đi vào database, bạn không cần viết query phức tạp để né dữ liệu bẩn về sau.
NUNIQUE với NULL▼

CREATE UNIQUE INDEX uq_active_email

● ● ●unique-null.sql
CREATE UNIQUE INDEX uq_active_email

Ràng buộc loại trừ

PostgreSQL có exclusion constraint để chống overlap, ví dụ không cho hai booking cùng phòng bị chồng thời gian.

● ● ●exclusion-constraint.sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE room_bookings
ADD CONSTRAINT no_room_overlap
EXCLUDE USING gist (
  room_id WITH =,
  tstzrange(start_at, end_at) WITH &&
);
S3 · Semi-structured Data
JSON Column: Khi NoSQL gặp SQL
JSON rất hữu ích cho metadata linh hoạt, nhưng nguy hiểm nếu bạn đưa dữ liệu core query path vào đó.
JKhi nào dùng JSON?▼
Dùng JSON khiKhông dùng JSON khi
Metadata thay đổi theo loại objectCột được lọc/sort/join thường xuyên

● ● ●json-index.sql
CREATE TABLE products (
  id BIGSERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  attrs JSONB NOT NULL
);
CREATE INDEX idx_products_attrs_gin ON products USING gin(attrs);
CREATE INDEX idx_products_color ON products ((attrs->>'color'));

MySQL
ALTER TABLE products
  ADD COLUMN color VARCHAR(30) GENERATED ALWAYS AS (JSON_UNQUOTE(attrs->'$.color')) STORED,
  ADD INDEX idx_products_color (color);

Oracle
CREATE SEARCH INDEX idx_products_attrs ON products(attrs) FOR JSON;
⚠️ Rule: Khi một JSON key bắt đầu xuất hiện trong WHERE/ORDER BY/JOIN thường xuyên, hãy cân nhắc tách thành column thật hoặc generated column.
S4 · Hierarchical Data

Dữ liệu dạng cây xuất hiện ở category, org chart, comment thread, menu, permission tree. Chọn sai model sẽ làm query đệ quy hoặc move node rất đắt.

● ● ●materialized-path.sql
CREATE TABLE categories (
  id BIGINT PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  path VARCHAR(500) NOT NULL
);

-- path ví dụ: /electronics/phone/android/

S5 · Physical Layout
Partition & bảng sắp xếp trước
Partition giúp quản lý dữ liệu lớn, đặc biệt là xóa/archive theo thời gian. Physical ordering giúp range scan tốt hơn, nhưng không thay thế index.
PPartition để xóa data lớn▼
● ● ●partitioning.sql
CREATE TABLE audit_logs (
  id BIGINT,
  created_at TIMESTAMPTZ NOT NULL,
  payload JSONB NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE audit_logs_2026_05 PARTITION OF audit_logs
FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');

-- Xóa cả tháng: DROP/TRUNCATE partition, không DELETE từng row

Oracle
CREATE TABLE audit_logs (
  id NUMBER,
  created_at TIMESTAMP NOT NULL,
  payload CLOB CHECK (payload IS JSON)
)
PARTITION BY RANGE (created_at)
INTERVAL (NUMTOYMINTERVAL(1, 'MONTH'))
(PARTITION p_init VALUES LESS THAN (TIMESTAMP '2026-01-01 00:00:00'));
⚠️ Partition không thay thế index: Partition pruning chỉ giảm số partition phải đọc. Trong mỗi partition, query vẫn cần index phù hợp.

S6 · Pre-computation
Khi index cũng không đủ nhanh
Nếu query phải tổng hợp quá nhiều dữ liệu mỗi lần chạy, index chỉ giúp một phần. Lúc này cần tính trước có kiểm soát.
SSummary table & materialized view▼
● ● ●precompute.sql
-- Summary table cho dashboard doanh thu theo ngày
CREATE TABLE daily_revenue (
  revenue_date DATE PRIMARY KEY,
  order_count BIGINT NOT NULL,
  total_amount NUMERIC(14,2) NOT NULL,
  refreshed_at TIMESTAMP NOT NULL
);

CREATE MATERIALIZED VIEW mv_daily_revenue AS
SELECT created_at::date AS revenue_date,
       COUNT(*) order_count,
       SUM(total_amount) total_amount
FROM orders
WHERE status = 'paid'
GROUP BY created_at::date;

Oracle
CREATE MATERIALIZED VIEW mv_daily_revenue
BUILD IMMEDIATE REFRESH FAST ON DEMAND AS
SELECT TRUNC(created_at) revenue_date, COUNT(*) order_count, SUM(total_amount) total_amount
FROM orders
WHERE status = 'PAID'
GROUP BY TRUNC(created_at);

S7 · Special Indexes
Các Index Đặc Thù Khác
Không phải lúc nào B-Tree cũng giải quyết được mọi bài toán. Spatial, Text và chuỗi dài đòi hỏi những loại index chuyên biệt.
1Tìm kiếm Không gian (Spatial Index) ▼

Khi tìm kiếm dữ liệu địa lý (tọa độ, khoảng cách, bán kính), B-Tree không thể xử lý tốt vì dữ liệu có 2 chiều (Latitude/Longitude). Giải pháp là dùng R-Tree hoặc GIST.

PostgreSQL
MySQL
Oracle
● ● ●postgis.sql
-- Yêu cầu extension PostGIS
CREATE EXTENSION postgis;
CREATE TABLE stores (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100),
  location GEOMETRY(Point, 4326)
);
-- Dùng GIST index
CREATE INDEX idx_stores_location ON stores USING GIST (location);

-- Tìm store trong bán kính 5km
SELECT name FROM stores 
WHERE ST_DWithin(location, ST_MakePoint(lng, lat)::geography, 5000);
● ● ●spatial.sql
CREATE TABLE stores (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100),
  location POINT NOT NULL SRID 4326,
  SPATIAL INDEX (location)
);

-- Tìm store bằng ST_Distance_Sphere
SELECT name FROM stores 
WHERE ST_Distance_Sphere(location, ST_PointFromText('POINT(lng lat)', 4326)) <= 5000;
● ● ●spatial.sql
-- Dùng Oracle Spatial (MDSYS.SDO_GEOMETRY)
CREATE TABLE stores (
  id NUMBER PRIMARY KEY,
  name VARCHAR2(100),
  location SDO_GEOMETRY
);
-- Đăng ký metadata cho cột spatial
INSERT INTO user_sdo_geom_metadata VALUES (
  'STORES', 'LOCATION', SDO_DIM_ARRAY(SDO_DIM_ELEMENT('X', -180, 180, 0.005), SDO_DIM_ELEMENT('Y', -90, 90, 0.005)), 4326
);
CREATE INDEX idx_stores_location ON stores(location) INDEXTYPE IS MDSYS.SPATIAL_INDEX;

-- Tìm store trong bán kính 5km
SELECT name FROM stores 
WHERE SDO_WITHIN_DISTANCE(location, SDO_GEOMETRY(2001, 4326, SDO_POINT_TYPE(lng, lat, NULL), NULL, NULL), 'distance=5000 unit=m') = 'TRUE';
2Trigram Index cho LIKE '%text%' ▼

Khi dùng chuỗi tìm kiếm bắt đầu bằng dấu % (vd: LIKE '%abc%'), B-Tree bị vô hiệu hóa vì không thể so sánh tiền tố. Thay vào đó, ta băm nhỏ chuỗi thành các cụm 3 ký tự (trigram).

PostgreSQL
MySQL
Oracle
● ● ●pg_trgm.sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
-- Hỗ trợ LIKE '%...' hoặc biểu thức chính quy (Regex) siêu nhanh
CREATE INDEX idx_users_name_trgm ON users USING GIN (name gin_trgm_ops);

SELECT * FROM users WHERE name ILIKE '%duc%';
📌 MySQL không có trigram chuyên dụng như Postgres. Thay vào đó, sử dụng FULLTEXT INDEX hoặc các search engine như Elasticsearch.
📌 Oracle sử dụng Oracle Text (CTXSYS.CONTEXT) để thực hiện Full-text search thay cho LIKE '%...%'.
3Giới hạn Index & Prefix Index ▼

B-Tree có giới hạn số bytes tối đa (vd: InnoDB MySQL giới hạn 3072 bytes). Nếu cột VARCHAR(5000) hoặc TEXT được đánh index, database sẽ từ chối. Giải pháp là đánh Prefix Index (Index tiền tố).

● ● ●prefix_index.sql
MySQL
-- Đánh index chỉ trên 50 ký tự đầu tiên của chuỗi
CREATE INDEX idx_articles_title ON articles(title(50));

-- Nếu chuỗi quá dài, bạn có thể tạo Hash Index (kích thước nhỏ gọn, dùng để so sánh =)
CREATE INDEX idx_session_token_hash ON sessions USING HASH (token);
⚠️ Trade-off: Prefix index không thể dùng cho ORDER BY hoặc GROUP BY, và cũng không thể đóng vai trò làm Covering Index được.
S8 · Practice & Error Catalog
Thực hành thiết kế schema & lỗi thường gặp
Áp dụng toàn bộ module vào một hệ thống order/log/event và nhận diện các lỗi schema khiến tuning về sau rất khó.
PPractice tasks▼
Task 1 — Thiết kế bảng orders

Thiết kế bảng orders cho OLTP: chọn PK, FK, status constraint, amount type, timestamp và index tối thiểu cho query theo user/status/created_at.

Dùng BIGINT hoặc UUIDv7 compact làm PK, NUMERIC/DECIMAL cho tiền, CHECK status IN (...), NOT NULL cho cột bắt buộc, index như (user_id, status, created_at DESC).

Task 2 — Thiết kế audit_logs theo tháng

Thiết kế bảng log 500M rows/năm, cần xóa log sau 180 ngày. Chọn partition key, retention strategy và index trong partition.

Partition range theo created_at theo tháng/ngày tùy volume. Retention bằng DROP/TRUNCATE PARTITION. Index theo query thật, ví dụ (tenant_id, created_at).

SSenior answer templates▼

Q1: Khi nào dùng JSON column?

Tôi dùng JSON cho metadata linh hoạt, ít cần constraint và không nằm trên critical query path. Nếu một key trong JSON bắt đầu được filter/sort/join thường xuyên, tôi sẽ tách thành column thật hoặc generated column rồi index. Với PostgreSQL có thể dùng JSONB + GIN/expression index; MySQL dùng generated column; Oracle có JSON search index.

Q2: Khi nào denormalize?

Khi query read-heavy phải join/aggregate quá nhiều và index không còn đủ, tôi cân nhắc denormalize hoặc summary table. Điều kiện là phải có chiến lược đồng bộ rõ ràng, kiểm soát stale data, test write amplification và có job kiểm tra consistency.

Q3: Thiết kế bảng log lớn cần xóa dữ liệu cũ thế nào?

Tôi partition theo thời gian nếu retention cũng theo thời gian. Xóa dữ liệu cũ bằng drop/truncate partition thay vì DELETE từng dòng. Sau đó vẫn tạo index trong partition theo query thật, ví dụ tenant/time hoặc service/time. Với Oracle có thể dùng interval partition để tự tạo partition mới.
