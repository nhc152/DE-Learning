Query shape ảnh hưởng execution plan

Subquery, EXISTS, IN hay JOIN — cùng một kết quả nhưng plan khác nhau. Optimizer hiện đại thường rewrite subquery thành semi join, anti join, nhưng không phải lúc nào cũng tối ưu. Biết shape đúng giúp không bị bất ngờ khi data tăng.

⚠️ Cảnh báo phổ biến: NOT IN với subquery có thể trả NULL sai logic. JOIN thay EXISTS khi không cần cột bên kia sẽ tạo duplicate rows không cần thiết.

DML cũng cần index và tuning

UPDATE và DELETE không chỉ "ghi dữ liệu" — database phải tìm dòng trước rồi mới khóa và sửa/xóa. Điều kiện WHERE tệ sẽ gây full scan và lock rộng, ảnh hưởng đến mọi transaction đang chạy song song.

📌 Rule: Trước DML lớn ở production, luôn chạy SELECT tương đương với EXPLAIN để kiểm tra số dòng scan và lock range.

Trước đây người ta giải quyết thế nào (sai)

  • Kéo toàn bộ data lên app rồi dedup bằng Python/Java → chậm và tốn memory.
  • Dùng OFFSET 100.000 để phân trang → càng về sau càng chậm theo tuyến tính.
  • Dùng nhiều vòng lặp SELECT → UPDATE theo từng row → cực chậm và lock dài.

S1 · Query Shape
Subquery không chậm như bạn nghĩ
Optimizer hiện đại thường rewrite subquery thành semi join hoặc anti join tương đương. Vấn đề nằm ở shape và index, không phải cứ có subquery là chậm.
📘 EXISTS vs IN vs JOIN ▼

Dùng EXISTS khi chỉ cần kiểm tra sự tồn tại

● ● ●exists-semi-join.sql
-- Câu hỏi: user nào đã từng mua hàng?
SELECT u.id, u.email
FROM users u
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.user_id = u.id
);

-- Index cần trên bảng con/probe side:
CREATE INDEX idx_orders_user_id ON orders(user_id);
💡 Mental model: EXISTS là "gặp một dòng hợp lệ thì dừng". Nếu bạn không cần cột từ bảng con, đừng JOIN rồi DISTINCT để khử trùng — tốn thêm một bước không cần thiết.

Anti join: tìm bản ghi không có quan hệ

● ● ●anti-join.sql
SELECT u.id
FROM users u
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.user_id = u.id
);

-- Tránh NOT IN nếu subquery có thể trả NULL:
WHERE id NOT IN (SELECT user_id FROM orders) -- dễ sai logic với NULL
PatternKhi dùngĐiểm DBA cần kiểm tra

INDanh sách nhỏ hoặc subquery đã uniqueNULL, cardinality, hash/semi join plan
JOINCần lấy cột từ bảng liên quanDuplicate rows, join order, index hai phía

S2 · DML Tuning
UPDATE & DELETE cũng cần index
DML không chỉ "ghi dữ liệu". Database vẫn phải tìm dòng trước, sau đó mới khóa và sửa/xóa. Điều kiện lọc tệ sẽ tạo full scan và lock rộng.
📘 Tối ưu WHERE của DML ▼

Anti-pattern: DELETE theo điều kiện không index

● ● ●dml-index.sql
-- Xóa log cũ: nếu created_at không có index/partition, DB phải scan rất nhiều
DELETE FROM audit_logs
WHERE created_at < '2025-01-01';

CREATE INDEX idx_audit_logs_created_at
ON audit_logs(created_at);

-- Với bảng cực lớn: ưu tiên partition rồi DROP/TRUNCATE partition

Batch nhỏ để giảm lock và undo/redo

● ● ●batch-delete.sql
PostgreSQL
WITH batch AS (
  SELECT id
  FROM audit_logs
  WHERE created_at < '2025-01-01'
  ORDER BY id
  LIMIT 5000
)
DELETE FROM audit_logs a
USING batch b
WHERE a.id = b.id;

Oracle
DELETE FROM audit_logs
WHERE rowid IN (
  SELECT rid FROM (
    SELECT rowid rid
    FROM audit_logs
    WHERE created_at < DATE '2025-01-01'
    ORDER BY id
  )
  WHERE ROWNUM <= 5000
);
⚠️ DBA rule: Trước khi chạy DML lớn ở production, luôn chạy SELECT tương đương với EXPLAIN để xem số dòng scan, index dùng và thứ tự khóa.
❓ Quiz nhanh — DML Tuning ▼

A. Để index scan nhanh hơn
B. Giảm lock time và undo/redo log, không block transaction khác lâu
C. Batch giúp tự tạo index tạm thời
S3 · DML Output
UPDATE JOIN, RETURNING và MERGE
Đẩy thao tác dữ liệu xuống database giúp giảm round-trip và tránh xử lý từng row ở tầng ứng dụng.
📘 Cập nhật từ bảng khác — 3 DB khác nhau ▼
● ● ●update-from-join.sql
PostgreSQL
UPDATE products p
SET stock = s.new_stock,
    updated_at = NOW()
FROM stock_import s
WHERE s.sku = p.sku;

MySQL
UPDATE products p
JOIN stock_import s ON s.sku = p.sku
SET p.stock = s.new_stock,
    p.updated_at = NOW();

Oracle
MERGE INTO products p
USING stock_import s
ON (s.sku = p.sku)
WHEN MATCHED THEN UPDATE SET
  p.stock = s.new_stock,
  p.updated_at = SYSTIMESTAMP;
✅ Index cần: products(sku) và stock_import(sku). Nếu source có duplicate SKU, MERGE/UPDATE có thể lỗi hoặc update không xác định — dedup source trước.

RETURNING: lấy dữ liệu ngay sau khi ghi

● ● ●returning.sql
PostgreSQL
INSERT INTO orders(user_id, status, total)
VALUES (42, 'pending', 990000)
RETURNING id, created_at;

UPDATE orders
SET status = 'paid'
WHERE id = 1001
RETURNING id, status, updated_at;

Oracle PL/SQL
UPDATE orders
SET status = 'PAID'
WHERE id = 1001
RETURNING status, updated_at INTO v_status, v_updated_at;
💡 Mental model: RETURNING tránh SELECT thêm sau DML — ít round-trip, an toàn hơn vì lấy dữ liệu đúng tại thời điểm write.

S4 · Cleanup
Xóa dòng trùng lặp bằng CTE
Dùng window function để đánh số bản ghi trùng, giữ lại một dòng đúng chuẩn và xóa phần còn lại trong database.
📘 ROW_NUMBER để dedup ▼
● ● ●deduplicate.sql
-- Giữ bản ghi mới nhất theo email, xóa các bản ghi còn lại
PostgreSQL
WITH ranked AS (
  SELECT id,
         ROW_NUMBER() OVER (
           PARTITION BY email
           ORDER BY updated_at DESC, id DESC
         ) AS rn
  FROM users
)
DELETE FROM users u
USING ranked r
WHERE u.id = r.id
  AND r.rn > 1;

Oracle
DELETE FROM users
WHERE rowid IN (
  SELECT rid
  FROM (
    SELECT rowid rid,
           ROW_NUMBER() OVER (
             PARTITION BY email
             ORDER BY updated_at DESC, id DESC
           ) rn
    FROM users
  )
  WHERE rn > 1
);
⚠️ Trước khi DELETE: chạy phần CTE dưới dạng SELECT để kiểm tra dòng nào bị xóa. Sau dedup, thêm unique constraint hoặc unique index để lỗi không quay lại.
S5 · Pagination
Phân trang đúng cách: keyset pagination
OFFSET sâu buộc database bỏ qua rất nhiều row. Keyset pagination dùng vị trí cuối cùng của trang trước để đi tiếp — O(1) thay vì O(N).
📘 OFFSET vs Keyset — so sánh thực tế ▼

OFFSET sâu: càng về sau càng chậm

● ● ●bad-pagination.sql
SELECT id, created_at, title
FROM posts
WHERE status = 'published'
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 200000;

Keyset: dùng last_seen key

● ● ●keyset-pagination.sql
PostgreSQL / MySQL
SELECT id, created_at, title
FROM posts
WHERE status = 'published'
  AND (
    created_at < '2026-05-25 10:00:00'
    OR (created_at = '2026-05-25 10:00:00' AND id < 98001)
  )
ORDER BY created_at DESC, id DESC
LIMIT 20;

CREATE INDEX idx_posts_feed
ON posts(status, created_at DESC, id DESC);

Oracle 12c+
SELECT id, created_at, title
FROM posts
WHERE status = 'PUBLISHED'
  AND (
    created_at < TIMESTAMP '2026-05-25 10:00:00'
    OR (created_at = TIMESTAMP '2026-05-25 10:00:00' AND id < 98001)
  )
ORDER BY created_at DESC, id DESC
FETCH FIRST 20 ROWS ONLY;

S6 · Concurrency
FOR UPDATE: khóa dòng ở tầng database
Dùng database lock khi nhiều worker cùng xử lý một tài nguyên. Khóa phải đi kèm index tốt để không khóa/scan quá rộng.
📘 Worker queue với SKIP LOCKED ▼
● ● ●for-update-skip-locked.sql
PostgreSQL
WITH picked AS (
  SELECT id
  FROM jobs
  WHERE status = 'pending'
  ORDER BY priority DESC, id
  LIMIT 10
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs j
SET status = 'processing', locked_at = NOW()
FROM picked p
WHERE j.id = p.id
RETURNING j.*;

CREATE INDEX idx_jobs_pick
ON jobs(status, priority DESC, id);

Oracle
SELECT id
FROM jobs
WHERE status = 'PENDING'
ORDER BY priority DESC, id
FETCH FIRST 10 ROWS ONLY
FOR UPDATE SKIP LOCKED;

-- Sau đó UPDATE các id đã lock trong cùng transaction.
Vấn đềCách xử lý
Worker đụng nhauFOR UPDATE SKIP LOCKED

DeadlockKhóa theo cùng thứ tự key trong mọi code path
Bộ đếm bị nghẽnShard counter, aggregate sau, hoặc dùng append event thay vì update một row nóng

S7 · Complex SQL
CTE: xử lý query phức tạp
CTE giúp chia query thành các bước dễ đọc. Điểm quan trọng với DBA là biết CTE có bị materialize hay optimizer có inline được không.
📘 CTE đúng mục đích ▼
● ● ●cte-report.sql
WITH paid_orders AS (
  SELECT id, user_id, total, created_at
  FROM orders
  WHERE status = 'paid'
    AND created_at >= '2026-05-01'
),
user_revenue AS (
  SELECT user_id, SUM(total) revenue
  FROM paid_orders
  GROUP BY user_id
)
SELECT u.id, u.email, r.revenue
FROM user_revenue r
JOIN users u ON u.id = r.user_id
ORDER BY r.revenue DESC
FETCH FIRST 100 ROWS ONLY;
📌 DB differences: PostgreSQL mới có thể inline CTE trong nhiều trường hợp; Oracle gọi CTE là subquery factoring và optimizer có thể dùng TEMP TABLE TRANSFORMATION; MySQL 8 hỗ trợ CTE nhưng cần EXPLAIN để kiểm tra materialization.

Khi nào dùng temp table thay CTE?

  • Kết quả trung gian dùng lại nhiều lần trong transaction hoặc batch job.
  • Cần tạo index riêng trên kết quả trung gian.
  • Query quá phức tạp khiến optimizer ước lượng sai nặng.
S8 · Advanced Tips
Tips query hữu ích khác
Các kỹ thuật nhỏ nhưng thực tế: biến range thành equality, thêm điều kiện giúp optimizer, xử lý hai điều kiện phạm vi và wildcard đầu chuỗi.
📘 Range, điều kiện ma, tìm kiếm ▼

Hai điều kiện range đụng nhau

● ● ●geo-range.sql
-- Tìm địa điểm trong bounding box: lat và lng đều là range
WHERE lat BETWEEN 10.7 AND 10.9
  AND lng BETWEEN 106.6 AND 106.8;

-- B-tree composite index chỉ tối ưu tốt range đầu tiên.
-- Giải pháp: geohash/tile/cell để biến một phần thành equality.
WHERE geo_cell IN ('w3gv1', 'w3gv2', 'w3gv3')
  AND lat BETWEEN 10.7 AND 10.9
  AND lng BETWEEN 106.6 AND 106.8;

CREATE INDEX idx_places_cell_lat_lng ON places(geo_cell, lat, lng);

Điều kiện "ma": không đổi kết quả, giúp optimizer

● ● ●ghost-condition.sql
-- App luôn chỉ hiển thị order 90 ngày gần nhất, nhưng query thiếu điều kiện thời gian
SELECT *
FROM orders
WHERE user_id = 42
  AND status = 'paid';

-- Thêm điều kiện giúp giảm phạm vi scan mà không đổi kết quả nghiệp vụ
SELECT *
FROM orders
WHERE user_id = 42
  AND status = 'paid'
  AND created_at >= CURRENT_DATE - INTERVAL '90 days';

Task 1 — Rewrite OFFSET pagination

Viết lại query feed dùng OFFSET 100000 sang keyset pagination. Chọn index phù hợp cho WHERE tenant_id = ? AND status = ? ORDER BY created_at DESC, id DESC.

Task 2 — Worker queue an toàn

Thiết kế query để 5 worker cùng lấy job pending mà không xử lý trùng. Nêu index cần thiết và lý do.

Dùng FOR UPDATE SKIP LOCKED trong transaction ngắn. Index theo pattern pick job: (status, priority DESC, id). Transaction phải commit ngay sau khi UPDATE status sang 'processing'.
