RRecovery & HA giải quyết vấn đề gì?▼

Backup là dữ liệu, recovery là năng lực

Hệ thống production không chỉ cần bản sao dữ liệu. Nó cần quy trình khôi phục đã được diễn tập, có người chịu trách nhiệm, có thời gian đo được và có tiêu chí xác nhận dữ liệu đúng.

Mental model: Backup là dù. Restore drill là lần bạn mở dù trước khi nhảy. HA là có máy bay thứ hai khi máy bay đầu gặp lỗi.

Các sự cố module này phải xử lý được

  • Developer xóa nhầm dữ liệu lúc 10:15.
  • Primary database mất disk hoặc node chết.
  • Replica lag quá xa hoặc replication bị broken.
  • Backup có nhưng restore mất lâu hơn SLA.
S1 · Strategy
RPO, RTO & Backup Strategy
Không thể thiết kế backup nếu chưa biết được phép mất bao nhiêu dữ liệu và phải khôi phục trong bao lâu.
SRPO/RTO là contract nghiệp vụ▼
Khái niệmCâu hỏiẢnh hưởng thiết kế
RPOĐược mất tối đa bao nhiêu dữ liệu?Tần suất backup/log shipping/sync replication
RTOPhải online lại trong bao lâu?Restore automation, standby, failover runbook
RetentionGiữ backup bao lâu?Storage, compliance, restore window
Failure domainBackup có sống nếu region/storage chết?Offsite/cross-region copy
⚠️ Rule: RPO/RTO phải được business chấp nhận. DBA không tự đoán “mất 1 giờ dữ liệu chắc ổn”.

S2 · PITR
Point-in-Time Recovery Fundamentals
PITR dùng base backup cộng transaction logs để khôi phục database tới một thời điểm trước lỗi.
PPITR flow▼
● ● ●pitr-flow.txt
Base backup lúc 00:00
    │
    ├─ WAL / binlog / archived redo từ 00:00 đến hiện tại
    │
    ├─ Sự cố xóa nhầm lúc 10:15
    │
    ▼
Restore base backup
    │
    ▼
Replay logs đến 10:14:59
    │
    ▼
Verify dữ liệu → cutover
🚨 Lưu ý: PITR yêu cầu log archive liên tục. Base backup không có WAL/binlog/archived redo thì chỉ khôi phục được tới thời điểm backup.
VVerify sau restore▼
  1. Kiểm tra database mở được và đúng target timestamp.
  2. Kiểm tra object count, row count, checksum nghiệp vụ quan trọng.
  3. Kiểm tra user/role/extension/procedure/job.
  4. Chạy smoke test app với database restored.
  5. Ghi lại thời gian restore thực tế so với RTO.
S3 · PostgreSQL
PostgreSQL WAL, Base Backup & Promotion
PostgreSQL PITR dựa trên base backup và WAL archive. Replica promotion cần runbook rõ để tránh split brain.
WWAL archive & base backup▼
● ● ●postgres-backup.conf
PostgreSQL
-- postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'

-- base backup
pg_basebackup -h primary -D /backup/base_20260525 -Fp -Xs -P

-- restore command trong recovery config
restore_command = 'cp /archive/%f %p'
recovery_target_time = '2026-05-25 10:14:59+07'
RReplication & promote▼
● ● ●postgres-replication.sql
PostgreSQL
SELECT application_name, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS bytes_lag
FROM pg_stat_replication;

-- promote standby
pg_ctl promote -D /var/lib/postgresql/data

-- hoặc SQL
SELECT pg_promote();
⚠️ Failover rule: Trước khi promote replica, phải đảm bảo primary cũ không còn nhận write, nếu không có nguy cơ split brain.
S4 · MySQL
MySQL Binlog, GTID & Replica Promotion
MySQL recovery dựa vào full backup cộng binary logs. GTID giúp failover/replication quản lý vị trí transaction rõ hơn.
BBinary log & PITR▼
● ● ●mysql-pitr.txt
MySQL
-- my.cnf
log_bin = mysql-bin
server_id = 1
gtid_mode = ON
enforce_gtid_consistency = ON

-- logical backup consistent cho InnoDB
mysqldump --single-transaction --routines --triggers --master-data=2 appdb > appdb.sql

-- replay binlog đến trước thời điểm lỗi
mysqlbinlog --stop-datetime='2026-05-25 10:14:59' mysql-bin.000123 | mysql appdb
📌 MySQL: Với DB lớn, dùng physical backup tool như MySQL Enterprise Backup, Percona XtraBackup hoặc snapshot storage thay vì chỉ mysqldump.
FReplica promotion▼
● ● ●mysql-failover.sql
MySQL
SHOW REPLICA STATUS\G

-- Trên replica được promote
STOP REPLICA;
RESET REPLICA ALL;
SET GLOBAL read_only = 0;
SET GLOBAL super_read_only = 0;

-- Các replica khác trỏ sang primary mới bằng GTID
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = 'new-primary',
  SOURCE_AUTO_POSITION = 1;
S5 · Oracle
Oracle RMAN, Archived Redo & Data Guard
Oracle có bộ công cụ recovery rất mạnh: RMAN cho backup/recovery, archived redo cho PITR, Data Guard cho HA/DR.
RRMAN backup & recovery▼
● ● ●oracle-rman.rman
Oracle RMAN
RMAN> CONFIGURE CONTROLFILE AUTOBACKUP ON;
RMAN> BACKUP DATABASE PLUS ARCHIVELOG;

-- PITR / incomplete recovery ví dụ
RMAN> RUN {
  SET UNTIL TIME "TO_DATE('2026-05-25 10:14:59','YYYY-MM-DD HH24:MI:SS')";
  RESTORE DATABASE;
  RECOVER DATABASE;
}

SQL> ALTER DATABASE OPEN RESETLOGS;
🚨 RESETLOGS: Đây là mốc incarnation mới. Runbook phải ghi rõ backup ngay sau incomplete recovery.
DData Guard switchover/failover▼
● ● ●oracle-dataguard.sql
Oracle Data Guard
SELECT name, value, unit
FROM v$dataguard_stats;

SELECT process, status, thread#, sequence#
FROM v$managed_standby;

-- Switchover planned maintenance
DGMGRL> SWITCHOVER TO standby_db;

-- Failover khi primary mất
DGMGRL> FAILOVER TO standby_db;
📌 Switchover vs Failover: Switchover là chuyển vai trò có kế hoạch, ít mất dữ liệu. Failover là phản ứng khi primary lỗi, cần đánh giá data loss theo protection mode/lag.
S6 · DR Runbooks
Failover, Switchover & DR Drill
High availability không phải chỉ có replica. Nó cần runbook, quyền thao tác, DNS/app cutover, verification và postmortem.
DFailover runbook tối thiểu▼
  1. Xác nhận sự cố primary: network, disk, process, monitoring, app errors.
  2. Freeze writes hoặc đảm bảo primary cũ không thể nhận write.
  3. Chọn replica tốt nhất: lag thấp nhất, dữ liệu đầy đủ nhất.
  4. Promote replica / Data Guard failover.
  5. Chuyển application connection/DNS/secret sang primary mới.
  6. Verify writes, critical reads, background jobs, replication mới.
  7. Ghi timeline, RPO/RTO thực tế, action items.
⚠️ Split brain là thảm họa: Không bao giờ để primary cũ và primary mới cùng nhận write.

SSenior answer templates▼

Q1: Bạn thiết kế backup strategy thế nào?

Tôi bắt đầu từ RPO/RTO và retention. Sau đó chọn physical backup cho database lớn, logical backup nếu cần object-level restore, log archiving để PITR, offsite/cross-region copy, encryption và restore drill định kỳ. Tôi không coi backup là đạt nếu chưa restore và verify dữ liệu.

Q2: Khi primary chết, bạn failover thế nào?

Tôi xác nhận sự cố, đảm bảo primary cũ không còn nhận write, chọn replica có lag thấp nhất, promote, chuyển app/DNS/connection string, verify read/write và thiết lập replication mới. Sau đó ghi lại RPO/RTO thực tế và làm postmortem.

Q3: PITR xử lý xóa nhầm dữ liệu ra sao?

Tôi restore base backup vào môi trường riêng, replay logs đến thời điểm ngay trước lệnh xóa, verify dữ liệu cần lấy lại, rồi chọn chiến lược: cutover toàn database hoặc trích xuất dữ liệu bị xóa để import lại production, tùy phạm vi lỗi và downtime cho phép.
