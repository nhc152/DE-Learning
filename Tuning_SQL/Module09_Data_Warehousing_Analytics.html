Report lớn không nên kéo OLTP xuống

OLTP phục vụ nghiệp vụ realtime: tạo order, thanh toán, cập nhật inventory. Analytical workload đọc nhiều tháng/năm dữ liệu, join rộng, group lớn. Chạy report nặng trực tiếp trên OLTP dễ làm chậm production.

Mental model: OLTP là quầy thu ngân. DWH là phòng phân tích. Đừng bắt quầy thu ngân vừa bán hàng vừa làm báo cáo chiến lược.
S1 · Workload Shape
OLTP vs OLAP
Cùng là SQL, nhưng mục tiêu tối ưu khác nhau: latency từng giao dịch so với throughput phân tích khối lượng lớn.
CSo sánh workload▼
Tiêu chíOLTPOLAP / DWH
QueryNhỏ, selective, nhiều transactionScan lớn, aggregate, join rộng
SchemaNormalized để ghi đúngStar/snowflake để đọc nhanh
IndexB-tree selective cho lookupPartition, bitmap/BRIN/MV/columnar tùy DB
ConcurrencyNhiều write nhỏBatch load + nhiều read/report
SLAp95/p99 request thấpReport hoàn thành trong window
⚠️ Rule: Đừng copy nguyên schema OLTP sang DWH rồi mong report nhanh. DWH cần thiết kế grain, dimension và aggregate riêng.
S2 · Modeling
Star Schema & Grain
Grain là mức chi tiết của fact table. Nếu grain không rõ, mọi report sau đó sẽ mơ hồ.
SFact và dimension▼
● ● ●star-schema.sql
CREATE TABLE dim_date (
  date_key INTEGER PRIMARY KEY,
  full_date DATE NOT NULL,
  month_key INTEGER NOT NULL,
  quarter INTEGER NOT NULL
);

CREATE TABLE dim_customer (
  customer_key BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  country VARCHAR(50),
  segment VARCHAR(50)
);

CREATE TABLE fact_sales (
  date_key INTEGER NOT NULL,
  customer_key BIGINT NOT NULL,
  product_key BIGINT NOT NULL,
  order_id BIGINT NOT NULL,
  quantity INTEGER NOT NULL,
  sales_amount NUMERIC(14,2) NOT NULL
);
📌 Grain ví dụ: Mỗi row trong fact_sales là một order line đã bán, không phải một order, một ngày hay một customer.

S4 · Loading
Partition, Batch Window & Incremental Load
DWH thường nạp dữ liệu theo batch hoặc micro-batch. Partition giúp load, drop, exchange và pruning tốt hơn.
PPartition theo thời gian▼
● ● ●dwh-partition.sql
PostgreSQL
CREATE TABLE fact_sales (
  date_key INTEGER NOT NULL,
  customer_key BIGINT NOT NULL,
  product_key BIGINT NOT NULL,
  sales_amount NUMERIC(14,2) NOT NULL
) PARTITION BY RANGE (date_key);

CREATE TABLE fact_sales_202605 PARTITION OF fact_sales
FOR VALUES FROM (20260501) TO (20260601);

Oracle
CREATE TABLE fact_sales (
  date_key NUMBER NOT NULL,
  customer_key NUMBER NOT NULL,
  sales_amount NUMBER(14,2) NOT NULL
)
PARTITION BY RANGE (date_key)
(PARTITION p202605 VALUES LESS THAN (20260601));
✅ DWH pattern: Load vào staging, validate, rồi exchange/attach partition để publish dữ liệu nhanh và rollback dễ.
S5 · Acceleration
Index, Bitmap & Materialized View
Analytical workload thường cần scan/aggregate lớn. Index B-tree không phải lúc nào là công cụ chính.
IIndex/MV theo database▼
● ● ●analytics-acceleration.sql
PostgreSQL
CREATE INDEX idx_fact_sales_date_brin
ON fact_sales USING brin(date_key);

CREATE MATERIALIZED VIEW mv_sales_daily AS
SELECT date_key, product_key, SUM(sales_amount) sales_amount
FROM fact_sales
GROUP BY date_key, product_key;

Oracle
CREATE BITMAP INDEX bmp_sales_product ON fact_sales(product_key);
CREATE BITMAP INDEX bmp_sales_customer ON fact_sales(customer_key);

CREATE MATERIALIZED VIEW mv_sales_daily
BUILD IMMEDIATE REFRESH FAST ON DEMAND ENABLE QUERY REWRITE AS
SELECT date_key, product_key, SUM(sales_amount) sales_amount, COUNT(*) cnt
FROM fact_sales
GROUP BY date_key, product_key;
⚠️ Oracle Bitmap Index: Rất mạnh cho DWH/OLAP, nhưng không dùng cho OLTP write-heavy vì lock/contention khi DML đồng thời.

SSenior answer templates▼

Q1: Thiết kế star schema bắt đầu từ đâu?

Tôi bắt đầu từ business process và grain của fact table. Sau đó xác định measures, dimensions, surrogate keys, natural keys và lịch sử thay đổi dimension. Nếu grain không rõ, report rất dễ double count hoặc mâu thuẫn.

Q2: Khi nào dùng materialized view?

Khi report lặp lại aggregate lớn và latency yêu cầu thấp hơn khả năng tính realtime. Tôi dùng materialized view hoặc summary table với refresh strategy rõ, kiểm tra freshness và reconciliation với source.

Q3: Làm sao tránh report làm chậm OLTP?

Tách workload bằng replica hoặc DWH, ETL/ELT theo batch/micro-batch, pre-aggregate dữ liệu nặng và giới hạn quyền/report query trên OLTP. Với report cần realtime, dùng bảng summary hoặc stream pipeline tùy SLA.
