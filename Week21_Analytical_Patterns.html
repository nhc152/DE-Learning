Vì sao analytics cần pattern tái sử dụng?

Khi công ty có nhiều dashboard, metric lệch nghĩa là chuyện rất thường gặp: mỗi analyst có thể tự chọn mẫu số khác nhau, thời gian khác nhau, hoặc định nghĩa user active khác nhau. Pattern giúp khóa logic chung để mọi team nhìn cùng một sự thật dữ liệu.

Framework dịch từ business sang SQL

  1. Business question: "Tỷ lệ thanh toán thành công theo nguồn traffic có giảm không?"
  2. Metric logic: Numerator = user hoàn tất payment, Denominator = user đến checkout, cùng time window 7 ngày.
  3. Pattern chọn: Funnel có order step + time constraint + first occurrence per user.
  4. Artifact: query + assumptions + quality checks + dashboard mapping.

Ví dụ SQL chuẩn hóa một metric contract (PostgreSQL/Oracle SQL khác cú pháp)

postgresql · metric_contract_example.sql
WITH checkout_users AS (
  SELECT user_id, MIN(event_time) AS first_checkout_at
  FROM events
  WHERE event_name = 'checkout_started'
    AND event_time >= DATE_TRUNC('day', CURRENT_DATE) - INTERVAL '7 days'
  GROUP BY user_id
),
paid_users AS (
  SELECT user_id, MIN(event_time) AS first_paid_at
  FROM events
  WHERE event_name = 'payment_success'
    AND event_time >= DATE_TRUNC('day', CURRENT_DATE) - INTERVAL '7 days'
  GROUP BY user_id
)
SELECT
  COUNT(DISTINCT p.user_id)::numeric / NULLIF(COUNT(DISTINCT c.user_id), 0) AS checkout_to_paid_rate
FROM checkout_users c
LEFT JOIN paid_users p
  ON c.user_id = p.user_id
 AND p.first_paid_at >= c.first_checkout_at
 AND p.first_paid_at <= c.first_checkout_at + INTERVAL '48 hours';

6. Bài Tập Thực Hành ▼
Bài 1 · Business question interpretation

Cho câu hỏi: "Trial conversion giảm trong 2 tuần gần đây, team cần biết lỗi ở đâu trong journey". Hãy viết lại thành metric contract gồm: numerator, denominator, grain, time window, exclusions.

Gợi ý lời giải:

  • Numerator: user trial có event payment_success trong 14 ngày kể từ trial_started.
  • Denominator: user có trial_started trong cùng kỳ.
  • Grain: user_id (không dùng event-level để tránh đếm trùng).
  • Exclusions: test user/internal account, duplicate payment event.
  • Time window: cohort trial bắt đầu trong 2 tuần gần nhất.
Bài 2 · SQL pattern selection

Match tình huống với pattern đúng:

  • a) "Muốn biết user quay lại sau ngày đầu tiên"
  • b) "Muốn biết user rớt ở bước nào trong onboarding"
  • c) "Muốn biết trạng thái subscription đổi thế nào theo thời gian"
  • a) Cohort Retention
  • b) Funnel Analysis
  • c) State Change Tracking

Lý do: mỗi pattern giải quyết một loại câu hỏi hành vi khác nhau; chọn sai pattern sẽ sai metric dù SQL đúng cú pháp.

Bài 3 · BI trust checklist

Thiết kế checklist 6 mục để review trước khi publish metric lên dashboard cho stakeholder.

  1. Định nghĩa numerator/denominator rõ.
  2. Time window có timezone chuẩn.
  3. Grain phù hợp (user/session/order...).
  4. Exclusion rules (internal/test/bot) rõ.
  5. Validation check với sample known cases.
  6. Tài liệu assumptions để tránh over-interpretation.

Transition detection bằng LAG (event-sourced)

postgresql · state_transition_lag.sql
WITH ordered AS (
  SELECT
    user_id,
    status,
    event_time,
    LAG(status) OVER (
      PARTITION BY user_id
      ORDER BY event_time
    ) AS prev_status
  FROM user_status_events
)
SELECT
  user_id,
  prev_status,
  status AS new_status,
  event_time AS transition_at
FROM ordered
WHERE prev_status IS NOT NULL
  AND prev_status <> status
  AND (prev_status, status) IN (
    ('active','inactive'),
    ('pending','completed'),
    ('trial','paid')
  );
oracle · state_transition_lag.sql
WITH ordered AS (
  SELECT
    user_id,
    status,
    event_time,
    LAG(status) OVER (
      PARTITION BY user_id
      ORDER BY event_time
    ) AS prev_status
  FROM user_status_events
)
SELECT
  user_id,
  prev_status,
  status AS new_status,
  event_time AS transition_at
FROM ordered
WHERE prev_status IS NOT NULL
  AND prev_status <> status
  AND (prev_status = 'active' AND status = 'inactive'
       OR prev_status = 'pending' AND status = 'completed'
       OR prev_status = 'trial' AND status = 'paid');

Dựng effective range từ stream event

Khi cần model kiểu SCD2 nhẹ cho phân tích, bạn có thể dùng LEAD(event_time) làm effective_to để có interval chính xác.

postgresql · effective_interval.sql
SELECT
  user_id,
  status,
  event_time AS effective_from,
  LEAD(event_time) OVER (
    PARTITION BY user_id
    ORDER BY event_time
  ) AS effective_to
FROM user_status_events
ORDER BY user_id, effective_from;
oracle · effective_interval.sql
SELECT
  user_id,
  status,
  event_time AS effective_from,
  LEAD(event_time) OVER (
    PARTITION BY user_id
    ORDER BY event_time
  ) AS effective_to
FROM user_status_events
ORDER BY user_id, effective_from;

Xử lý duplicate status events

Nhiều hệ thống gửi lại cùng một event do retry network. Nếu không deduplicate, bạn sẽ đếm thừa số lần transition.

Rule production quan trọng: event_time dùng để sắp thứ tự lifecycle (nghĩa business), còn ingested_at dùng để chọn bản ghi canonical khi deduplicate (nghĩa pipeline). Không nên hoán đổi hai vai trò này.

deduplicate_status_events.sql
WITH ranked AS (
  SELECT
    user_id,
    status,
    event_time,
    source_event_id,
    ROW_NUMBER() OVER (
      PARTITION BY source_event_id
      ORDER BY ingested_at
    ) AS rn
  FROM user_status_events_raw
)
SELECT user_id, status, event_time, source_event_id
FROM ranked
WHERE rn = 1;
✅ Rule production: luôn xác định khóa duplicate trước (source_event_id hoặc business key + event_time) rồi mới chạy LAG/LEAD.
⚠️ Khi có late-arriving events, cần recompute lại phần interval bị ảnh hưởng (ví dụ lookback 3-7 ngày hoặc theo watermark), không chỉ append ngày mới; nếu không timeline transition sẽ lệch.
📌 Nếu không có event_id, dùng fallback key: (entity_id, status, date_trunc('second', event_time)) và đánh dấu mức độ tin cậy.

postgresql · cohort_retention_d0_d30.sql
WITH cohort_base AS (
  SELECT
    user_id,
    DATE(MIN(event_time AT TIME ZONE 'Asia/Ho_Chi_Minh')) AS cohort_date
  FROM events
  WHERE event_name = 'signup_started'
  GROUP BY user_id
),
activity AS (
  SELECT DISTINCT
    e.user_id,
    DATE(e.event_time AT TIME ZONE 'Asia/Ho_Chi_Minh') AS activity_date
  FROM events e
  WHERE e.event_name IN ('app_opened','project_viewed','task_completed')
),
retention AS (
  SELECT
    c.cohort_date,
    (a.activity_date - c.cohort_date) AS day_offset,
    COUNT(DISTINCT a.user_id) AS retained_users
  FROM cohort_base c
  JOIN activity a
    ON c.user_id = a.user_id
   AND a.activity_date >= c.cohort_date
   AND a.activity_date <= c.cohort_date + INTERVAL '30 day'
  GROUP BY c.cohort_date, day_offset
),
cohort_size AS (
  SELECT cohort_date, COUNT(*) AS cohort_users
  FROM cohort_base
  GROUP BY cohort_date
),
data_cutoff AS (
  SELECT MAX(activity_date) AS data_cutoff_date
  FROM activity
)
SELECT
  r.cohort_date,
  r.day_offset,
  r.retained_users,
  cs.cohort_users,
  ROUND(r.retained_users::numeric / NULLIF(cs.cohort_users,0), 4) AS retention_rate,
  CASE
    WHEN r.day_offset = 30 AND r.cohort_date + INTERVAL '30 day' > d.data_cutoff_date THEN 0
    ELSE 1
  END AS is_mature_period
FROM retention r
JOIN cohort_size cs ON r.cohort_date = cs.cohort_date
CROSS JOIN data_cutoff d
WHERE r.day_offset IN (0,1,7,30)
ORDER BY r.cohort_date, r.day_offset;

Rolling metrics là logic nhìn lại một khoảng thời gian

Metric dạng rolling trả lời câu hỏi theo cửa sổ thời gian trượt. Ví dụ: tại ngày 2026-05-12, rolling 7-day active users đếm user có ít nhất một sự kiện từ 2026-05-06 đến 2026-05-12. Ngày hôm sau, cửa sổ dịch sang 2026-05-07 đến 2026-05-13.

Rolling 7-day active users

Với distinct users, nhiều database không hỗ trợ COUNT(DISTINCT user_id) trực tiếp trong window frame một cách tối ưu. Pattern an toàn là tạo calendar date, join vào activity trong range, rồi group lại theo ngày báo cáo.

rolling_metrics.sql · PostgreSQL
WITH calendar AS (
  SELECT generate_series(DATE '2026-04-01', DATE '2026-04-30', INTERVAL '1 day')::date AS report_date
),
daily_activity AS (
  SELECT DISTINCT
    user_id,
    DATE(occurred_at AT TIME ZONE 'Asia/Ho_Chi_Minh') AS activity_date
  FROM fact_product_events
  WHERE event_name IN ('app_opened', 'lesson_started', 'purchase_completed')
)
SELECT
  c.report_date,
  COUNT(DISTINCT da.user_id) AS rolling_7d_active_users
FROM calendar c
LEFT JOIN daily_activity da
  ON da.activity_date BETWEEN c.report_date - INTERVAL '6 days' AND c.report_date
GROUP BY c.report_date
ORDER BY c.report_date;
rolling_metrics.sql · Oracle SQL
WITH calendar AS (
  SELECT DATE '2026-04-01' + LEVEL - 1 AS report_date
  FROM dual
  CONNECT BY DATE '2026-04-01' + LEVEL - 1 <= DATE '2026-04-30'
),
daily_activity AS (
  SELECT DISTINCT
    user_id,
    TRUNC(CAST((FROM_TZ(CAST(occurred_at AS TIMESTAMP), 'UTC') AT TIME ZONE 'Asia/Ho_Chi_Minh') AS DATE)) AS activity_date
  FROM fact_product_events
  WHERE event_name IN ('app_opened', 'lesson_started', 'purchase_completed')
)
SELECT
  c.report_date,
  COUNT(DISTINCT da.user_id) AS rolling_7d_active_users
FROM calendar c
LEFT JOIN daily_activity da
  ON da.activity_date BETWEEN c.report_date - 6 AND c.report_date
GROUP BY c.report_date
ORDER BY c.report_date

Moving average cho revenue hoặc orders

Nếu metric là additive theo ngày, window function đơn giản hơn. Revenue daily có thể dùng AVG(revenue) OVER hoặc SUM(revenue) OVER theo frame.

moving_average.sql
WITH daily_revenue AS (
  SELECT
    order_date,
    SUM(net_revenue) AS revenue
  FROM fct_orders
  GROUP BY order_date
)
SELECT
  order_date,
  revenue,
  AVG(revenue) OVER (
    ORDER BY order_date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ) AS revenue_7d_moving_avg
FROM daily_revenue
ORDER BY order_date;

Streak và gap-and-island

Streak là chuỗi ngày liên tiếp. Pattern phổ biến: lấy ngày active duy nhất theo user, đánh số bằng ROW_NUMBER(), rồi tạo khóa đảo bằng activity_date - row_number. Các ngày liên tiếp sẽ có cùng island key.

gap_and_island_trace.txt
user_id | activity_date | rn | island_key
u_101   | 2026-04-01    | 1  | 2026-03-31
u_101   | 2026-04-02    | 2  | 2026-03-31
u_101   | 2026-04-03    | 3  | 2026-03-31
u_101   | 2026-04-06    | 4  | 2026-04-02
u_101   | 2026-04-07    | 5  | 2026-04-02

Giải thích:
- 2026-04-01 → 2026-04-03 có cùng island_key => cùng một streak.
- 2026-04-04 và 2026-04-05 không active => tạo gap.
- 2026-04-06 bắt đầu island mới => streak mới.
streak_analysis.sql · PostgreSQL
WITH active_days AS (
  SELECT DISTINCT user_id, occurred_at::date AS activity_date
  FROM fact_product_events
  WHERE event_name IN ('app_opened', 'lesson_completed')
),
numbered AS (
  SELECT
    user_id,
    activity_date,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY activity_date) AS rn
  FROM active_days
),
islands AS (
  SELECT
    user_id,
    activity_date,
    activity_date - (rn::int * INTERVAL '1 day') AS island_key
  FROM numbered
)
SELECT
  user_id,
  MIN(activity_date) AS streak_start,
  MAX(activity_date) AS streak_end,
  COUNT(*) AS streak_days
FROM islands
GROUP BY user_id, island_key
ORDER BY streak_days DESC, user_id;

multidimensional_aggregation.sql · PostgreSQL
SELECT
  CASE
    WHEN GROUPING(channel) = 0 AND GROUPING(country) = 0 AND GROUPING(device_type) = 0 THEN 'channel_country_device'
    WHEN GROUPING(channel) = 0 AND GROUPING(country) = 0 THEN 'channel_country'
    WHEN GROUPING(channel) = 0 THEN 'channel'
    ELSE 'overall'
  END AS aggregation_level,
  COALESCE(channel, '(all)') AS channel,
  COALESCE(country, '(all)') AS country,
  COALESCE(device_type, '(all)') AS device_type,
  COUNT(DISTINCT user_id) AS buyers,
  SUM(net_revenue) AS net_revenue
FROM fct_orders
WHERE order_date BETWEEN DATE '2026-04-01' AND DATE '2026-04-30'
GROUP BY GROUPING SETS ((channel, country, device_type), (channel, country), (channel), ())
ORDER BY aggregation_level, net_revenue DESC;

Attribution basics

First-touch gán credit cho nguồn đầu tiên trong attribution window. Last-touch gán credit cho nguồn gần conversion nhất. Multi-touch chia credit theo rule đã thống nhất. Đây là mô hình mô tả, không phải bằng chứng causal.

attribution_basic.sql
WITH eligible_touches AS (
  SELECT
    o.order_id,
    o.net_revenue,
    t.marketing_source,
    ROW_NUMBER() OVER (PARTITION BY o.order_id ORDER BY t.touch_time) AS first_touch_rank,
    ROW_NUMBER() OVER (PARTITION BY o.order_id ORDER BY t.touch_time DESC) AS last_touch_rank
  FROM fct_orders o
  JOIN fact_marketing_touches t
    ON t.user_id = o.user_id
   AND t.touch_time <= o.order_time
   AND t.touch_time >= o.order_time - INTERVAL '30 days'
  WHERE o.user_id NOT IN (SELECT user_id FROM internal_accounts)
    AND LOWER(COALESCE(t.user_agent, '')) NOT LIKE '%bot%'
)
SELECT
  marketing_source,
  SUM(CASE WHEN first_touch_rank = 1 THEN net_revenue ELSE 0 END) AS first_touch_revenue,
  SUM(CASE WHEN last_touch_rank = 1 THEN net_revenue ELSE 0 END) AS last_touch_revenue
FROM eligible_touches
GROUP BY marketing_source
ORDER BY last_touch_revenue DESC;
⚠️ Anti-pattern: nói "source A tạo revenue" mà không ghi first-touch, last-touch, attribution window, identity rule và caveat.

# Week 21 Analytical Patterns

## Business questions answered
- Which users changed status from trial to paid, active to inactive, or pending to completed?
- Where do users drop in the signup funnel?
- What is D1, D7, and D30 retention by acquisition cohort?
- How are rolling active users and moving revenue trend changing?
- Which users have the longest consecutive active-day streak?
- How much revenue is attributed to marketing sources under first-touch and last-touch models?

## Input tables
- fact_product_events(user_id, session_id, event_name, occurred_at, event_id, device_type, country)
- user_status_events(user_id, status, status_changed_at, event_id)
- dim_users(user_id, signup_at, acquisition_channel, country)
- fct_orders(order_id, user_id, order_time, net_revenue, channel, country, device_type)
- fact_marketing_touches(user_id, touch_time, marketing_source, campaign_id, touch_id)

## Assumptions
- Reporting timezone is Asia/Ho_Chi_Minh unless noted otherwise.
- Active user means at least one qualifying event: app_opened, lesson_started, lesson_completed, purchase_completed.
- Funnel conversion requires ordered steps within 7 days from signup_started.
- Cohort denominator is fixed at cohort size on D0.
- Attribution window is 30 days before order_time.
- Attribution is descriptive, not causal proof.

## Validation checks
- State history has no overlapping effective windows per user.
- Funnel step counts are monotonic decreasing after order enforcement.
- Cohort retention never uses a changing denominator.
- Rolling active users use a complete data cutoff.
- Streak input has one row per user_id and activity_date.
- Attributed revenue reconciles against eligible order revenue.

# Metric Definitions

## d7_retention_rate
- Numerator: cohort users active exactly 7 days after cohort_date.
- Denominator: cohort_size at D0.
- Cohort: signup date unless query states first activity cohort.
- Caveat: immature cohorts are flagged.

## rolling_7d_active_users
- Numerator: distinct users active from report_date - 6 through report_date.
- Grain: report_date.
- Caveat: report_date must pass freshness cutoff.

## attributed_revenue_last_touch_30d
- Revenue assigned to latest eligible touch before order.
- Eligibility: touch_time between order_time - 30 days and order_time.
- Caveat: descriptive model, not incrementality.

validation_queries.sql

validation_queries.sql
-- 1) State history: không overlap hiệu lực
SELECT user_id, COUNT(*) AS overlap_rows
FROM (
  SELECT
    user_id,
    effective_from,
    effective_to,
    LAG(effective_to) OVER (
      PARTITION BY user_id
      ORDER BY effective_from
    ) AS prev_effective_to
  FROM user_status_history
) x
WHERE prev_effective_to IS NOT NULL
  AND effective_from < prev_effective_to
GROUP BY user_id
HAVING COUNT(*) > 0;

-- 2) Funnel: step count phải giảm dần sau order enforcement
WITH funnel_counts AS (
  SELECT
    COUNT(*) AS step1_users,
    COUNT(t2) AS step2_users,
    COUNT(t3) AS step3_users,
    COUNT(t4) AS step4_users
  FROM funnel_joined_ordered
)
SELECT *
FROM funnel_counts
WHERE NOT (
  step1_users >= step2_users
  AND step2_users >= step3_users
  AND step3_users >= step4_users
);
