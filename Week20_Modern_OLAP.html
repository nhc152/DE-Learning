3. Giải Thích Chi Tiết▼

Tại sao traditional databases thường hụt hơi với analytics?

OLTP database tối ưu cho transaction nhỏ và point lookup. Dashboard analytics lại cần scan nhiều bản ghi, aggregate nhiều chiều, phục vụ nhiều user cùng lúc. Khi nhét workload này vào OLTP, bạn gặp CPU spike, lock pressure, query tail latency cao.

Dashboard cần gì hơn việc "lưu dữ liệu"?

  • Latency: trả kết quả ở mức giây hoặc sub-second cho chart/filter.
  • Freshness: dữ liệu đủ mới cho quyết định vận hành.
  • Concurrency: nhiều người mở cùng dashboard không nghẽn.
  • Cost control: query lặp lại phải tối ưu bằng pre-aggregation/materialization.

Định nghĩa SLA thực hành: theo dõi cả p50/p95/p99 (không chỉ average). Ví dụ p95 = 95% query trả về dưới ngưỡng X giây; đây là chỉ số rất quan trọng cho dashboard production.

Bài 1 · Engine selection task

Scenario: Dashboard product có 150M events/ngày, 120 PM mở cùng lúc, filter 7 ngày gần nhất, target p95 < 1.5s. Hãy chọn lớp serving phù hợp và lý do.

Ưu tiên ClickHouse hoặc Druid/Pinot style serving. Lý do: read-heavy, high concurrency, aggregate theo thời gian; OLTP không phù hợp. Nếu yêu cầu near real-time cao, cân nhắc Druid/Pinot; nếu batch/stream hybrid và team SQL mạnh, ClickHouse thường thực dụng hơn.

Bài 2 · Dashboard workload analysis

Liệt kê 3 tín hiệu cho thấy hệ hiện tại đang "store tốt nhưng serve kém".

  • Query latency tăng mạnh khi số dashboard user tăng.
  • CPU DB transaction tăng theo giờ họp dashboard.
  • Nhiều query aggregate phải chạy lại từ raw table, không có pre-aggregation.

3. Giải Thích Chi Tiết▼

OLTP mindset

Row-oriented storage giúp lấy/cập nhật một vài dòng rất nhanh. Đó là lý do tốt cho checkout, payment, user profile, nhưng không lý tưởng cho query kiểu "đếm theo segment trong 90 ngày".

OLAP mindset

Columnar storage + vectorized execution giúp engine đọc đúng cột cần dùng và xử lý theo batch vector CPU-friendly. Kết quả là throughput query analytics cao hơn đáng kể.

Minh họa trực quan: cùng câu hỏi, khác engine

ClickHouse (OLAP)
-- Dashboard query chạy mỗi 15 giây
SELECT date_trunc('hour', o.created_at) AS hour_bucket,
       p.category,
       count(*) AS orders
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
WHERE o.created_at >= now() - interval '30 days'
GROUP BY 1, 2

Trên OLTP schema normalize, join fanout lớn + scan dài ngày dễ làm p95 latency tăng mạnh khi concurrency cao.

-- Bảng denormalized cho serving
SELECT event_hour,
       category,
       count() AS orders
FROM orders_analytics
WHERE event_date >= today() - 30
GROUP BY event_hour, category
ORDER BY event_hour, orders DESC;

Trên OLAP serving table, query shape gọn hơn, scan cột cần thiết và tận dụng partition/order key để giảm latency.

Anti-pattern: Dùng normalized OLTP schema để nuôi dashboard high-volume rồi đổ lỗi "SQL chậm".

6. Bài Tập Thực Hành▼
Bài 1 · Query pattern critique

Đánh giá truy vấn: join 7 bảng OLTP normalized + group by theo giờ 30 ngày để render dashboard mỗi 10 giây. Hãy chỉ ra 3 vấn đề kiến trúc.

  • Join fanout lớn trên schema không tối ưu analytics.
  • Không có pre-aggregation/materialized layer cho query lặp lại.
  • Polling 10 giây trên OLTP gây nhiễu workload transaction.
Bài 2 · Engine selection task

Team BI chạy report theo ngày, không yêu cầu real-time, governance quan trọng. Chọn lớp chính và giải thích.

Warehouse managed là lớp chính (BigQuery/Snowflake). Lý do: governance, lineage, transformation/marts mạnh; Modern OLAP chỉ bổ sung nếu xuất hiện yêu cầu latency thấp và concurrency dashboard cao.

DuckDB basics cho DE

DuckDB chạy embedded, phù hợp trên laptop/CI job/notebook. Bạn có thể query trực tiếp file dữ liệu mà không cần dựng server DB trước.

DuckDB SQL over Parquet
SELECT event_date,
       event_type,
       count(*) AS events,
       count(DISTINCT user_id) AS users
FROM read_parquet('data/events/*.parquet')
WHERE event_date >= current_date - INTERVAL 7 DAY
GROUP BY event_date, event_type
ORDER BY event_date, events DESC;

Vì sao phù hợp cho prototyping?

  • Không chờ provisioning warehouse chỉ để thử một query idea.
  • Dễ tái lập trong CI để check row count, null spike, schema drift cơ bản.
  • Kết hợp tốt với Parquet làm artifact trung gian trong pipeline.

Limitations cần nhớ

  • Không phải distributed serving engine cho dashboard nhiều user đồng thời.
  • Không thay warehouse đa team với governance và workload isolation.
  • Không nên gánh workload update/delete transactional kiểu OLTP.
  • Với dataset lớn hơn RAM máy local, các query join/aggregate phức tạp có thể gây áp lực memory và tăng spill-to-disk time.
Note: Khi chạy DuckDB trên laptop RAM yếu, hãy đặt memory limit hợp lý, tách query theo stage, và ưu tiên scan cột cần thiết để giảm nguy cơ OOM.
Anti-pattern: Dùng DuckDB để thay toàn bộ hạ tầng warehouse production nhiều team.

Nêu 2 lý do tại sao chuyển CSV sang Parquet thường giúp query DuckDB nhanh hơn.

  • Compression + metadata statistics hỗ trợ skip data block tốt hơn.

MergeTree mindset

ClickHouse không tự cứu thiết kế bảng tệ. Bạn cần chọn partition theo time (thường month/day) và order key theo filter/group-by phổ biến.

Nguyên tắc vàng ORDER BY: đưa cột filter thường xuyên nhất lên trước, ưu tiên cột cardinality thấp-trung bình trước cột cardinality rất cao để tăng hiệu quả data skipping.

Schema mẫu event analytics
CREATE TABLE events_olap
(
  event_time DateTime,
  event_date Date MATERIALIZED toDate(event_time),
  user_id UInt64,
  session_id String,
  event_type LowCardinality(String),
  platform LowCardinality(String),
  country LowCardinality(String),
  revenue Float64
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)
ORDER BY (event_date, event_type, platform, user_id)
TTL event_date + INTERVAL 6 MONTH;
Note: LowCardinality(String) thường phù hợp cho cột có distinct values thấp (ví dụ thường dưới ~10k). Không nên áp dụng cho cột như user_id.
Pruning intuition
Query filter: event_date=2026-05-01 AND event_type='purchase'
-> Engine đọc metadata min/max theo granule
-> Skip phần lớn granules không thỏa điều kiện
-> Chỉ scan vùng dữ liệu liên quan thay vì toàn bộ partition

Query mẫu dashboard

Aggregation query
SELECT event_date,
       event_type,
       count(*) AS events,
       uniqExact(user_id) AS users,
       sum(revenue) AS gross_revenue
FROM events_olap
WHERE event_date >= today() - 14
  AND platform IN ('ios','android')
GROUP BY event_date, event_type
ORDER BY event_date, events DESC;

Điểm mạnh và giới hạn

  • Strength: tốc độ aggregate cao, compression tốt, phù hợp dashboard concurrency cao.
  • Weakness: update/delete không theo kiểu OLTP; mutation lớn có cost đáng kể.
  • Operational: schema/table design có tác động trực tiếp đến hiệu năng và chi phí.
Warn: Ingest lắt nhắt (single-row/few-row inserts liên tục) dễ gây "Too many parts" và merge pressure. Hãy batch insert (ví dụ mỗi 1-5 giây hoặc theo ngưỡng số dòng) để giữ cụm MergeTree ổn định.
Anti-pattern: Thiết kế ClickHouse như normalized OLTP schema với quá nhiều join runtime.

Bài 2 · Ingestion reasoning

Khi nào nên dùng batch insert trước Kafka ingestion cho ClickHouse?

Nếu freshness yêu cầu ở mức phút, batch insert đơn giản và ổn định hơn về vận hành. Kafka ingestion phù hợp khi cần near real-time và team đủ năng lực stream ops.

Freshness vs correctness

Freshness càng cao thì áp lực xử lý late event, dedup và reprocessing càng lớn. Bạn cần quyết định mức "chấp nhận sai số tạm thời" cho dashboard vận hành.

Tình huốngƯu tiênGợi ý
Fraud monitoring theo phútFreshnessNear real-time + correction window hậu kỳ
Finance closingCorrectnessBatch + reconciliation kỹ
Product live metricsCân bằngReal-time for trend, warehouse for truth set

Data Retention cho real-time OLAP

Realtime analytics không chỉ là ingest nhanh, mà còn là quản lý vòng đời dữ liệu. Bạn cần policy retention rõ: giữ raw segment bao lâu, rollup segment bao lâu, và khi nào archive/delete để kiểm soát cost.

  • Hot segment: giữ dữ liệu chi tiết gần hiện tại để query realtime.
  • Warm/history: dữ liệu cũ hơn có thể giữ mức rollup thấp hơn.
  • Retention policy: xóa/archival định kỳ để tránh storage phình to theo thời gian.
Anti-pattern: Dựng Real-time OLAP chỉ vì "nghe hiện đại" trong khi business chấp nhận report theo giờ/ngày.

Query shape matters

Cùng một engine, query tốt và query tệ có thể chênh 10-100x. Tránh SELECT * trong dashboard, chỉ lấy cột cần thiết và filter time window rõ ràng.

Materialized view pattern

MV ý tưởng
CREATE MATERIALIZED VIEW mv_daily_events
ENGINE = SummingMergeTree
PARTITION BY toYYYYMM(event_date)
ORDER BY (event_date, event_type, platform)
AS
SELECT event_date,
       event_type,
       platform,
       count() AS events,
       uniqCombined64(user_id) AS users_approx
FROM events_olap
GROUP BY event_date, event_type, platform;

Approximate aggregations

Với distinct user cardinality cao, dùng hàm approximate (ví dụ uniqCombined/approx_count_distinct tùy engine) giảm tài nguyên và latency đáng kể.

Anti-pattern phổ biến

  • Tạo quá nhiều materialized views nhưng không có owner và usage metric.
  • Partition theo cột hiếm dùng để filter khiến pruning kém.
  • Không review dashboard query sau khi business đổi logic.
Note: Tối ưu bền vững = theo dõi query heatmap + chi phí + tần suất sử dụng, không chỉ benchmark 1 lần.

Build vs Buy

  • Build/open-source: linh hoạt cao, tối ưu cost dài hạn nếu đội mạnh ops.
  • Buy/managed: time-to-value nhanh, giảm burden hạ tầng, đổi lại chi phí dịch vụ.

Self-hosted vs Cloud/Managed burden

Nếu self-hosted ClickHouse/Druid, team phải tự gánh monitoring cluster, backup/restore, upgrade version, tuning merge/index, và xử lý incident hạ tầng. Với team mỏng, lựa chọn managed thường thực tế hơn trong giai đoạn đầu.

  • Self-hosted: kiểm soát sâu, nhưng cần năng lực SRE/Platform ổn định.
  • Managed cloud: giảm khối lượng vận hành nền, phù hợp khi ưu tiên tốc độ delivery.

Team maturity là biến số thật

Nếu team chưa có monitoring/query governance/chủ ownership rõ, chọn engine quá phức tạp sẽ tăng nợ vận hành nhanh hơn lợi ích hiệu năng.

Anti-pattern: Chọn engine chỉ vì "công ty lớn dùng" mà không kiểm tra fit với workload và năng lực team hiện tại.
