🧠 2. Bốn "Mindset" Ăn Điểm Team Ấn Độ

Khi phỏng vấn, hãy lồng ghép 4 từ khóa này vào câu trả lời để chứng tỏ bạn là một Architect thực thụ:

  • "Garbage in, Garbage out": Tôi không bao giờ tin dữ liệu nguồn. Dữ liệu lỗi phải nằm lại vùng Staging/Quarantine, tuyệt đối không đẩy rác vào Core mới.
  • Metadata-Driven over Hard-coding: Nếu có 1000 bảng, tôi không viết 1000 script. Tôi thiết kế 1 Framework chạy bằng bảng cấu hình (Control Schema) để tự động sinh lệnh SQL.
  • Design for Failure: Migration Terabytes dữ liệu chắc chắn sẽ có lúc đứt cáp, lock DB. Hệ thống phải có Checkpoint/Restartability (lỗi ở đâu, bật lại chạy tiếp ở đó).
  • Reconciliation is Non-negotiable: Script chạy Success không có ý nghĩa. Thành công là khi đối soát độc lập chứng minh 100% khớp nhau về số dòng và giá trị tài chính.

🚀 3. Quy trình Migration 4 Phase Chuẩn Doanh nghiệp

  • Phase 1: Discovery & Assessment (Khảo sát): Phân tích Data Profiling, đánh giá chất lượng nguồn. Mapping & Gap Analysis. Tính toán Volume/Capacity.
  • Phase 2: Migration Architecture Design (Thiết kế): Quyết định chiến lược (Trickle vs Big Bang). Thiết kế Staging/Landing Zone. Xây dựng Data Reconciliation Framework.
  • Phase 3: Execution & Dry-run (Chạy thử): Code Metadata-driven Pipeline bằng PySpark/Oracle PL/SQL. Tổ chức Dry-run trên môi trường Staging để đo đạc Execution Time Window và Performance Tuning.
  • Phase 4: Cutover & Go-Live (Di cư thật): Chuẩn bị Runbook theo từng phút. Kích hoạt Checksum cuối. Có sẵn kịch bản quay đầu (Rollback Strategy) nếu gặp sự cố nghiêm trọng.

Cách trình bày 5 Bước khi vẽ (Nói bằng tiếng Anh):

  • Step 1: Topology Design: "I separate the flow into 3 layers: Source, Staging (with Masking for PII), and Target Core."
  • Step 2: Metadata-driven Framework: "I don't hardcode. The ETL engine is driven by a Metadata Config schema (the yellow box)."
  • Step 3: Zero-Downtime Strategy: "I use 2 pipelines. Bulk Load for history, and CDC (GoldenGate/Debezium) for real-time transactions."

  • Step 5: Reconciliation: "Finally, the Reconciliation Engine (blue box) independently compares Source and Target using Row-count, Amount, and Checksum."

🛠 4. Thiết Kế Database Thực Chiến (Whiteboard / Technical Design)

Interviewer rất hay yêu cầu bạn thiết kế cấu trúc lưu trữ và đối soát.

A. Thiết kế bảng Metadata (Dùng để chạy Tự động - Framework)

Thay vì hardcode, bạn tạo 1 Schema điều khiển tên là MIGRATION_CTRL:

CREATE TABLE migration_metadata_config (
    table_id          NUMBER PRIMARY KEY,
    source_table      VARCHAR2(100),
    target_table      VARCHAR2(100),
    load_strategy     VARCHAR2(50),  -- Ví dụ: 'TRUNCATE_LOAD', 'CDC_UPSERT'
    partition_key     VARCHAR2(50),
    is_active         CHAR(1) DEFAULT 'Y'
);

CREATE TABLE migration_batch_control (
    batch_id          NUMBER PRIMARY KEY,
    table_id          NUMBER REFERENCES migration_metadata_config(table_id),
    start_time        TIMESTAMP,
    end_time          TIMESTAMP,
    status            VARCHAR2(20),  -- 'RUNNING', 'FAILED', 'COMPLETED'
    rows_processed    NUMBER,
    checkpoint_val    VARCHAR2(100)  -- Dùng để Restartability
);

B. SQL Đối Soát 3 Lớp (Data Reconciliation)

-- Lớp 1: Row-Count Balance (Đếm dòng)
SELECT COUNT(*) FROM source.txn_table WHERE value_date = :biz_date;
SELECT COUNT(*) FROM target.txn_table WHERE value_date = :biz_date;

-- Lớp 2: Financial Numeric Aggregation (Tổng số tiền)
SELECT SUM(amount) FROM source.txn_table WHERE value_date = :biz_date;
SELECT SUM(amount) FROM target.txn_table WHERE value_date = :biz_date;

-- Lớp 3: Data Hash/Checksum (Kiểm tra lệch data)
-- Dùng hàm HASH mã hóa nối chuỗi các cột quan trọng
SELECT DBMS_CRYPTO.HASH(
    UTL_I18N.STRING_TO_RAW(account_id || '|' || amount || '|' || currency, 'AL32UTF8'), 
    2 -- HASH_MD5
) AS row_hash
FROM source.txn_table;

🗣 5. Kịch Bản Hỏi - Đáp (Scenario-based Q&A)

Q1: "Làm sao anh đảm bảo dữ liệu di cư sang hệ thống mới chính xác 100% không bị mất mát?"
Tư duy trả lời: Trình bày Framework đối soát 3 lớp (3-Layer Reconciliation Framework).

"To ensure 100% data integrity, I design an independent 3-Layer Data Reconciliation Framework.
- Level 1 (Row-count): Validate total records between Source and Target.
- Level 2 (Financial Aggregation): Compare SUM(AMOUNT) to ensure not a single cent is lost.
- Level 3 (Data Hash/Checksum): For critical tables like CUSTOMER or TRANSACTION, I generate a SHA-256 or MD5 hash on core columns in both databases. If the hashes match, the data is perfectly identical without any silent corruption."
Q2: "Hệ thống Core Banking chạy 24/7, nếu anh migrate bảng Transaction hàng tỷ dòng, anh xử lý bài toán Downtime thế nào?"
Tư duy trả lời: Kết hợp Bulk Load lịch sử + CDC (Zero-Downtime Migration).

"For a 24/7 Core Banking system, Big Bang is impossible. I propose a Hybrid Strategy using Historical Load combined with CDC (Change Data Capture).
- Phase 1 (Historical Load): I migrate historical data (e.g., 5 years back) weeks before Go-Live using Direct Path Insert (APPEND hint in Oracle Exadata) during off-peak hours to minimize performance impact.
- Phase 2 (Delta Load via CDC): For live transactions, I configure CDC tools like Oracle GoldenGate or Debezium for Postgres to replicate INSERT/UPDATE directly from Redo Logs/WAL.
- On Cutover day, the two systems are fully synced, and we only need a 5-minute window to switch traffic from legacy to target."
Q3: "Hãy giải thích cách anh thiết kế một Metadata-driven Migration Framework?"
Tư duy trả lời: Tách biệt logic và cấu hình.

"Instead of hard-coding 100 scripts for 100 tables, I decouple the migration logic using a Control Schema. I create tables like MIGRATION_METADATA_CONFIG storing Source_Table, Target_Table, and Mapping_Logic.
Then, I write a Master PySpark Pipeline or a Master Stored Procedure that reads this config table and dynamically generates SQL statements using EXECUTE IMMEDIATE. If the business adds 50 new tables, we don't write new code; we just insert 50 rows into the control table."
Q4: "Khi đưa dữ liệu lên môi trường Test (UAT), anh xử lý vấn đề bảo mật dữ liệu nhạy cảm (PII) thế nào?"
Tư duy trả lời: Thể hiện tư duy Data Governance, Data Masking.

"Security is critical in banking. I implement Data Masking and Obfuscation for all non-prod environments. During the migration to Staging/UAT, I use tools or native functions like DBMS_CRYPTO in Oracle to mask PII data (e.g., masking the last 4 digits of a credit card or scrambling names). This ensures we comply with data privacy regulations while testers still have production-like data shapes to work with."
