1. Kịch Bản Thiết Kế ERD & Bảng Biểu (System Design)

Phân hệ lưu trữ giao dịch và xử lý cảnh báo rửa tiền (AML) với 4 bảng cốt lõi:

  • CUSTOMER (1) — (N) ACCOUNT: Khách hàng có nhiều tài khoản.
  • ACCOUNT (1) — (N) TRANSACTION: Tài khoản phát sinh nhiều giao dịch.
  • TRANSACTION (1) — (0..N) AML_ALERT: Giao dịch sinh ra cảnh báo rủi ro.

Thiết kế chi tiết cấu trúc (Oracle 19c DDL)

-- 1. BẢNG DANH MỤC KHÁCH HÀNG
CREATE TABLE CUSTOMER (
    CUSTOMER_ID   NUMBER(19,0) NOT NULL,
    FULL_NAME     VARCHAR2(150) NOT NULL,
    ID_CARD       VARCHAR2(256) NOT NULL, -- Sẽ được Encrypt bằng DBMS_CRYPTO (hoặc pgcrypto trong Postgres)
    PHONE         VARCHAR2(256),          
    STATUS        VARCHAR2(20) DEFAULT 'ACTIVE',
    CREATED_AT    TIMESTAMP DEFAULT SYSTIMESTAMP,
    CONSTRAINT PK_CUSTOMER PRIMARY KEY (CUSTOMER_ID)
);

-- 2. BẢNG TÀI KHOẢN NGÂN HÀNG
CREATE TABLE ACCOUNT (
    ACCOUNT_NO    VARCHAR2(20) NOT NULL,
    CUSTOMER_ID   NUMBER(19,0) NOT NULL,
    ACCT_TYPE     VARCHAR2(10) NOT NULL,
    BALANCE       NUMBER(18,2) DEFAULT 0.00, -- Tuyệt đối không dùng FLOAT để tránh sai số
    CURRENCY      VARCHAR2(3) DEFAULT 'VND',
    STATUS        VARCHAR2(20) DEFAULT 'OPEN',
    CREATED_AT    TIMESTAMP DEFAULT SYSTIMESTAMP,
    CONSTRAINT PK_ACCOUNT PRIMARY KEY (ACCOUNT_NO),
    CONSTRAINT FK_ACCOUNT_CUSTOMER FOREIGN KEY (CUSTOMER_ID) REFERENCES CUSTOMER(CUSTOMER_ID)
);

💡 Điểm Specialist cần nhấn mạnh:
- Kiểu dữ liệu: Số tiền luôn dùng NUMBER(18,2) (hoặc DECIMAL trong Postgres), không bao giờ dùng FLOAT.
- Bảo mật: PII (ID_CARD, PHONE) mã hóa AES256 từ vùng ODS (bằng DBMS_CRYPTO hoặc pgcrypto) theo luật An toàn thông tin.

2. Kịch Bản Đánh Index & Partitioning (Bảng Tỷ Dòng)

Đối với bảng TRANSACTION lên tới trăm triệu dòng mỗi tháng, quy hoạch vật lý là bắt buộc.

-- 3. BẢNG GIAO DỊCH (TỶ DÒNG) - Bỏ Physical Foreign Key để tối ưu INSERT
CREATE TABLE TRANSACTION (
    TXN_ID         NUMBER(19,0) NOT NULL,
    ACCOUNT_NO     VARCHAR2(20) NOT NULL,
    TXN_TYPE       VARCHAR2(10) NOT NULL,
    AMOUNT         NUMBER(18,2) NOT NULL,
    TXN_DATE       DATE NOT NULL,         -- Khóa phân vùng (Partition Key)
    DESCRIPTION    VARCHAR2(250),
    CHANNEL        VARCHAR2(20)
)
PARTITION BY RANGE (TXN_DATE) (
    PARTITION SUB_TXN_2026_M04 VALUES LESS THAN (TO_DATE('2026-05-01', 'YYYY-MM-DD')),
    PARTITION SUB_TXN_2026_M05 VALUES LESS THAN (TO_DATE('2026-06-01', 'YYYY-MM-DD')),
    PARTITION SUB_TXN_DEFAULT VALUES LESS THAN (MAXVALUE)
);

-- TẠO LOCAL INDEX
CREATE INDEX IX_TXN_ACCT_DATE ON TRANSACTION (ACCOUNT_NO, TXN_DATE) LOCAL;

-- 4. BẢNG CẢNH BÁO AML (HỆ THỐNG NGHIỆP VỤ)
CREATE TABLE AML_ALERT (
    ALERT_ID      NUMBER(19,0) NOT NULL,
    TXN_ID        NUMBER(19,0) NOT NULL,
    RULE_CODE     VARCHAR2(30) NOT NULL, -- Ví dụ: R01_HIGH_VOLUME_CASH
    RISK_LEVEL    VARCHAR2(10),          -- HIGH, MEDIUM, LOW
    ALERT_DATE    TIMESTAMP DEFAULT SYSTIMESTAMP,
    STATUS        VARCHAR2(20) DEFAULT 'NEW', -- NEW, INVESTIGATING, CLOSED
    CONSTRAINT PK_AML_ALERT PRIMARY KEY (ALERT_ID)
);

Chiến lược giải thích với Khách hàng:

  • Partition Pruning: Truy vấn theo tháng (TXN_DATE) sẽ chỉ quét đúng partition của tháng đó, tốc độ tăng gấp hàng trăm lần.
  • Data Purging an toàn: Khi cần dọn data 5 năm trước, thay vì dùng lệnh DELETE gây treo DB (tốn Undo/WAL), chỉ cần dùng ALTER TABLE TRANSACTION DROP PARTITION (chạy mất 0.5s).
  • Local Index: Khách hàng thường tra cứu lịch sử của 1 tài khoản trong 1 tháng. Dùng Local Index để khi Drop partition, các index khác vẫn USABLE.
  • Bỏ Physical FK: Đề xuất không tạo Foreign Key trỏ về bảng ACCOUNT để tối đa tốc độ INSERT realtime. Việc check tính toàn vẹn đưa lên tầng Application hoặc ETL.

3. Công Việc Hằng Ngày (Daily Tasks & Troubleshooting)

Trả lời mạch lạc theo quy trình 3 giai đoạn của DBA/Specialist:

Ca sáng (08h00 - 09h30): Health Check

  • Kiểm tra Dashboard Grafana (Prometheus exporter) / Dynatrace: CPU, RAM, IOPS, Active Sessions, Buffer Hit Ratio (> 95%).
  • Kiểm tra trạng thái đồng bộ HA: Oracle Data Guard (Apply Lag) hoặc PostgreSQL Replication Slot xem có bị lag không.
  • Check các Batch Job ETL đêm qua xem có job nào FAIL hoặc Long-running không.

Ca ngày (09h30 - 16h30): Performance Tuning

  • Bắt Slow Query: Dùng AWR Report (Oracle) hoặc pg_stat_statements (PostgreSQL).
  • Dùng EXPLAIN PLAN / EXPLAIN ANALYZE để xem câu lệnh bị Full Table Scan hay Optimizer tính sai Cardinality do thống kê cũ (Stale stats).
  • Phối hợp Dev review SQL trước khi deploy lên UAT/PROD.

Cuối ngày / Cuối tuần: Bảo trì (Maintenance)

  • Theo dõi dung lượng Tablespace (Capacity Planning).
  • Chạy script thu gom rác (VACUUM trên PostgreSQL) hoặc cập nhật thống kê (DBMS_STATS.GATHER_SCHEMA_STATS trên Oracle) vào ban đêm.

🔥 Vũ khí bí mật - Quy trình xử lý sự cố (Treo DB):
1. Tìm Root Cause: Không đoán mò. Check Wait Events bằng V$SESSION_WAIT / ASH (Oracle) hoặc pg_stat_activity / pg_locks (Postgres) xem Session nào đang gây row lock contention.
2. Workaround khẩn cấp: Xin phê duyệt KILL SESSION gây nghẽn luồng giao dịch.
3. Permanent Fix: Mang câu SQL về Test mổ xẻ Plan, thêm Index hoặc chỉnh Partition để dứt điểm.

4. Kịch Bản Data Architecture & Migration (Corporate Banking)

Khi được hỏi về xây dựng hệ thống mới (Migration), ứng viên Data Architecture tuyệt đối không trả lời theo kiểu "Tắt server cũ, chép data, bật server mới" (Big Bang). Hệ thống Corporate Banking (Khách hàng Doanh nghiệp) với hàng trăm Entity phức tạp (Thư tín dụng L/C, Tài trợ thương mại, Giải ngân khoản vay) yêu cầu cách tiếp cận Migration an toàn, Multi-Phase.

1. Chiến lược Migration: Strangler Fig Pattern & Parallel Run

  • Strangler Fig Pattern: Không đập bỏ toàn bộ Core Legacy cùng lúc. Chia nhỏ từng domain (Ví dụ: Cắt riêng Module Tiền gửi có kỳ hạn ra trước). Lớp API Gateway sẽ làm nhiệm vụ Router: Request cũ đi vào DB Oracle cũ, Request mới vào DB PostgreSQL mới.
  • Change Data Capture (CDC): Dùng Kafka Connect + Debezium (hoặc Oracle GoldenGate) để đồng bộ (Sync) dữ liệu 2 chiều real-time giữa DB cũ và DB mới. Mục đích: Nếu hệ thống mới có lỗi nghiêm trọng, ta có thể Fallback (quay xe) về hệ thống cũ ngay lập tức mà không bị thất thoát giao dịch.
  • Parallel Run & Reconciliation (Đối soát): Chạy ngầm cả hai hệ thống trong 1-3 tháng. Thiết kế các Batch Job (ETL) chạy cuối ngày để đối chiếu Tổng tài sản, Số dư tài khoản giữa Core cũ và Core mới. Nếu sai số = 0 trong 30 ngày liên tục mới được Sign-off để Cut-over hoàn toàn.

2. Thiết kế Kiến trúc Dữ liệu mới (Microservices Data Architecture)

  • Database-per-service (Tách DB): Phá vỡ DB Monolithic khổng lồ. Domain Khách hàng (CIF) quản lý bởi 1 DB chuẩn hóa (Master Data Management). Domain Tín dụng (Lending) sở hữu DB riêng. Giải quyết triệt để vấn đề "Một bảng chết kéo theo toàn hệ thống chết".
  • CQRS & Tách biệt OLTP/OLAP: Database Core chỉ tập trung xử lý Transaction (OLTP) với tốc độ cao. Dữ liệu ngay lập tức được stream (qua Kafka) về một Data Lake / Data Warehouse (như ClickHouse, Hadoop, hoặc Greenplum) để chạy báo cáo cuối ngày (OLAP). Tránh tình trạng sếp kéo báo cáo làm treo DB giao dịch.
  • Event-Driven & SAGA Pattern: Trong kiến trúc mới không thể JOIN 2 bảng ở 2 DB khác nhau. Data Architect phải thiết kế cơ chế giao tiếp bằng Event. Để đảm bảo tính toàn vẹn (ACID), thay vì dùng Two-Phase Commit (2PC) rất chậm, phải áp dụng SAGA Pattern (nếu service B lỗi thì gọi API báo service A rollback lại tiền).

💡 Điểm Data Architect cần "Đóng đinh" hội đồng:
- "Thưa anh/chị, Migration không phải là bài toán Copy SQL Data, mà cốt lõi là bài toán Đối soát (Reconciliation) và Fallback Plan (Kế hoạch lùi)."
- "Xây DB Microservices không khó ở việc tạo bảng, mà khó ở việc quản trị Master Data (MDM) để tránh dữ liệu rác, và đảm bảo Eventual Consistency (Nhất quán cuối) khi chia tách dữ liệu."
