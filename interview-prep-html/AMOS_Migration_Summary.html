Pattern Stored Procedure — logging architecture

Cấu trúc procedure chuẩn (SDB → MDB)

CREATE OR REPLACE PROCEDURE MDB.TRANSFROM_BASIC_03_XMEASURE AS
  v_insert_count NUMBER := 0;
  V_error_message VARCHAR2(500);
BEGIN
  -- 1. Truncate target table (Truncate & Load pattern)
  EXECUTE IMMEDIATE 'TRUNCATE TABLE MDB.XMEASURE';

  -- 2. Log start time vào MNT schema
  DELETE MNT.XTABLE_EXPORT_STATS WHERE XTABLE='XMEASURE';
  INSERT INTO MNT.XTABLE_EXPORT_STATS (XTABLE, NUM_ROWS, START_TIME)
    VALUES ('XMEASURE', v_insert_count, sysdate);
  COMMIT;

  -- 3. Transform: INSERT SELECT DISTINCT từ SDB
  INSERT INTO MDB.XMEASURE
    SELECT DISTINCT * FROM SDB.XMEASURE;
  COMMIT;

  -- 4. Đếm row + log end time
  SELECT COUNT(*) INTO v_insert_count FROM MDB.XMEASURE;
  UPDATE MNT.XTABLE_EXPORT_STATS
    SET NUM_ROWS=v_insert_count, END_TIME=sysdate
    WHERE XTABLE='XMEASURE';
  COMMIT;

EXCEPTION WHEN OTHERS THEN
  V_error_message := SQLERRM;
  DBMS_OUTPUT.PUT_LINE('Error: ' || V_error_message);
END;
/
Pattern tương đồng AML
Giống ETL_BATCH_LOG + ETL_STEP_LOG trong dự án AML: cùng pattern 2-layer logging, Truncate & Load, track start/end time per table
Data quality xử lý
Null date từ AMASIS = 01/01/0001 → procedure riêng sau load để convert về NULL. Đây là data quality fix tích hợp vào pipeline.

📌 "Kể về một dự án migration bạn đã làm"

"Tôi tham gia dự án migrate dữ liệu từ hệ thống AMASIS trên IBM AS400 sang AMOS aviation maintenance application tại VAECO — Vietnam Airlines Engineering Company, do NGS thực hiện cho đối tác Swiss AviationSoftware. Đây là migration lớn với tổng khoảng 36 triệu records, thực hiện qua nhiều rehearsal trước khi Go-live production.

Architecture tôi thiết kế gồm 3 layer rõ ràng: AMASIS extract xuống Staging DB dạng raw (SDB schema) qua CSV trung gian dùng SQL*Loader, transform và clean sang MDB schema bằng Oracle Stored Procedures, rồi export TXT files để AMOS application import. Mỗi layer có logging riêng qua bảng XTABLE_EXPORT_STATS ghi lại row count, start/end time từng table.

Thách thức lớn nhất là tối ưu cutover window xuống dưới 60 tiếng — vì đây là production system của hãng hàng không. Chiến lược tôi áp dụng là phased cutover 3 giai đoạn: preload 26 triệu records historical trước khi freeze, cutover phase chỉ còn xử lý 9.9 triệu records gần đây nhất. Sau Rehearsal 1, tôi đạt được 47 tiếng so với mục tiêu 60 tiếng.

Một bài học quan trọng là data quality của source system — AMASIS export null date thành 01/01/0001. Thay vì xử lý thủ công, tôi đã build procedure fix và tích hợp cố định vào pipeline, tiết kiệm ~1 tiếng mỗi lần chạy và tránh lỗi lặp lại."

📌 "Bạn xử lý rollback plan thế nào?" (câu hỏi khó)

"Trong dự án AMOS, chúng tôi thực hiện nhiều rehearsal trước Go-live chính xác vì lý do này — mỗi rehearsal là cơ hội để test cả forward và rollback path. Về mặt kỹ thuật, SDB schema giữ nguyên raw data từ AMASIS cho đến khi cutover được xác nhận thành công, vì vậy nếu có vấn đề ở bất kỳ giai đoạn nào, chúng tôi có thể re-run từ checkpoint. AMASIS vẫn là system of record cho đến khi Go-live được approval — đây là nguyên tắc quan trọng nhất: không bao giờ decommission source system trước khi migration được validate đầy đủ."

📌 "Làm sao validate dữ liệu sau migration?"

"Chúng tôi có hai lớp validation: đầu tiên là row count check sau mỗi step dùng wc -l và COUNT(*) từ XTABLE_EXPORT_STATS, so sánh với row count từ source. Thứ hai là business rule validation — VAECO team kiểm tra dữ liệu nghiệp vụ trực tiếp trên MIG2 environment trước khi confirm cutover. Nhìn lại thì đây là điểm cần cải thiện — nếu làm lại tôi sẽ bổ sung checksum validation và automated reconciliation report thay vì chỉ row count."

⚠️ Điểm cần cải thiện trong dự án này

Reconciliation — chỉ dùng wc -l (row count). Nên có checksum + business total validation (SUM của amount, balance...)
Rollback plan — implicit (dựa vào SDB còn đó). Nên document rõ: ai approve rollback, rollback trong bao lâu, criteria để trigger
Formal cutover runbook — cần có step-by-step với người phụ trách từng bước, expected time, go/no-go criteria
Vendor dependency management — KUS cung cấp scripts muộn là risk thực tế. Cần SLA contract + buffer time chính thức
